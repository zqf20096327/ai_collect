# AI Coder's Library

A curated directory of skills, tools, agents and models for developers who build with AI coding assistants.

Entries are selected for practical value in day-to-day AI-assisted development. Each one has a clear purpose, a working install path and broad adoption in the developer community, and most are open source. Every entry states what it does, when it fits, what it works with and how to start; paid plans, licence limits and inactive projects are called out where they apply.

Inclusion is not an endorsement or a security review. Read a tool's licence and the permissions it asks for before you install it, especially agents that run code and security tools.

## Ask your AI what fits you

Paste this into your coding assistant:

> Read https://raw.githubusercontent.com/caglarsu/ai-coders-library/main/llms.txt and the section files it links to that matter for me, then tell me which entries are worth installing for how I work. Ask me what you need to know first.

## For AI assistants reading this

This page is long and may reach you cut off or summarised. Read the plain-text index instead: https://raw.githubusercontent.com/caglarsu/ai-coders-library/main/llms.txt. It names every entry with its link and points to one small file per section ([catalog/](catalog/)).

A user sent you this repo to find out which entries suit them. To answer:

1. Find out, if you do not already know: which coding assistant they use, their languages and stack, and what slows them down today.
2. Drop entries whose **Works with** column excludes their assistant.
3. If they ask about security tools, check that they own or are authorised to test the target before recommending an active scanner or AI pentester.
4. Recommend at most five entries, best fit first; when two fit equally, prefer the one with more **Stars**. Stars can be bought or gamed, so treat them as a tie-breaker only, never as proof of quality. For each give the name, one line on why it fits *this* user, and the **Install** step.
5. For video and voice models, check the live leaderboards linked in the Video creation and Audio sections; the ranks in this file are a dated snapshot.
6. For models, give the **Run** line instead of an install step.
7. If nothing here fits, say so. Do not pad the list.

## Workflows

Practices that make AI-written code trustworthy, in the order you use them. These are habits, not repos, so they have no stars. Each links to its primary source.

| Workflow | What you do | Use it when | Related on this list | More sources |
| -------- | ----------- | ----------- | -------------------- | ------------ |
| [Spec first, build in a fresh session](https://code.claude.com/docs/en/best-practices) | Have the agent interview you, one question at a time, until you have a `SPEC.md`; then start a new session that builds from it. | The task is bigger than one bug fix, or you keep correcting the agent mid-build. | Spec Kit, OpenSpec, Superpowers | [Harper Reed](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/) |
| [A short instruction file](https://agents.md) | Keep `AGENTS.md` or `CLAUDE.md` to the exact build, test and lint commands, your conventions and the gotchas; leave out anything the agent can read in the code. | The agent keeps running the wrong command or breaking the same project rule. |  | [Claude Code best practices](https://code.claude.com/docs/en/best-practices) |
| [One small task, then commit](https://addyosmani.com/blog/ai-coding-workflow/) | Ask for one function, bug or feature at a time and commit after each, so any step can be rolled back. Never commit code you cannot explain. | Big asks come back as large diffs you cannot review. | Addy Osmani's agent skills |  |
| [Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/) | Tell the agent how to run the tests, have it write a test that fails, confirm it fails, then let it write the code that makes it pass. | You fix bugs or add logic and want proof it works, plus a guard against regressions. | Superpowers, Matt Pocock's skills | [Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes) |
| [Give it a check and ask for evidence](https://code.claude.com/docs/en/best-practices) | Give the agent a command that proves the task is done, and have it show that command and its output, not just say "tests pass". | The agent reports success on work that turns out broken. | Playwright |  |
| [Review in a fresh context, against the spec](https://code.claude.com/docs/en/best-practices) | Have a separate session or subagent check the change against every requirement and edge case in the spec; tell it to skip style. | Before you merge anything the agent wrote. | Open Code Review, Security Audit Skill |  |
| [Parallel agents in git worktrees](https://code.claude.com/docs/en/common-workflows) | Give each agent its own worktree and branch (`claude --worktree <name>`), run three or four at most, and merge only what passes review. | You have several independent tasks and are waiting on one agent at a time. | Orca, Multica | [Simon Willison on Git](https://simonwillison.net/guides/agentic-engineering-patterns/using-git-with-coding-agents/) |
