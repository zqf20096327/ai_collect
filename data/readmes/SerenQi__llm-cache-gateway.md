# LLM 缓存网关 · 把 26,460 token 的上下文压到只为 221 个付费

一个 OpenAI 兼容的转发网关。它做的事只有一件：**让长上下文对话尽可能命中上游的 prompt cache。**

实测单次请求：上下文 26,460 token，其中 **26,239 命中缓存**，真正按新 token 计费的只有 **221 个**。

| 指标 | 数值 |
| --- | --- |
| 单次请求上下文 | 26,460 tokens |
| 其中缓存命中 | 26,239 tokens |
| 实际新增计费 | 221 tokens |
| **缓存命中率** | **99.16%** |

> **这是连续对话场景下的单次实测峰值，不是长期平均值。**
> 缓存过期后的第一次请求不但省不到，还要付出高于基础价的写入费用——真实平均值取决于对话密度，详见第六节。

**关于成本**：调优前后，单次对话成本从约 \$1.5 降到约 \$0.02。
但这个区间内同时还调整了上下文管理与模型选择，**该降幅含缓存及同期其他优化，不应全部归因于本项目**。
可独立归因于缓存的硬数据只有上表那一行。

**成熟度**：5 分钟 TTL 这条主路径经过数月日常使用，稳定。
本仓库修复的两个 bug 与 1 小时 TTL 开关**仅通过单元测试，未经真实流量验证**。

## 一、要解决的问题

用大模型做长对话，最贵的不是模型答了多少，是**每一轮都要把整段历史重新发一遍**。

对话进行到第 50 轮时，上下文可能有几万 token。每问一句，这几万 token 全额重新计费一次。成本随轮次线性增长，到后期，你付的钱九成以上是在为"模型重读一遍你们之前说过的话"买单。

Anthropic 提供了 prompt cache：命中的部分按约 1/10 计价。问题是——**它非常难稳定命中。**

## 二、为什么难

prompt cache 的命中条件是：**请求的前缀必须逐字节一致。**

差一个字符，整段缓存作废。而实际系统里破坏前缀一致性的因素到处都是：

1. 客户端每轮注入的时间戳、状态信息在变
2. 动态检索的上下文（比如从记忆库里查出来的内容）每轮不同
3. 消息结构被中间层改写
4. **请求被路由到了不同的上游供应商**

第 4 条是最隐蔽的：OpenRouter 这类聚合平台会在多个供应商之间路由（Anthropic 官方 / AWS Bedrock / Google Vertex 都能跑 Claude），而**缓存存在于各供应商自己那边，互不共享**。这次打到 Anthropic、下次被分流到 Bedrock，缓存直接归零，而你完全察觉不到。

## 三、方案

分两层，缺一层都到不了 99%。

### 第一层：锁死上游供应商（客户端侧）

```json
{"order": ["anthropic"], "allow_fallbacks": false}
```

只走 Anthropic，且**禁止 fallback**——宁可这次请求失败，也不接受被静默分流到别的供应商。这是**用可用性换缓存一致性**。

大部分讲 prompt caching 的资料只教怎么打断点，不提这一条。但如果每次请求落在不同后端，断点打得再准也没有意义。

### 第二层：自动插入缓存断点（网关侧）

核心是 `add_cache_hints_openai()`，打两个断点：

**断点 1 — system 消息**
挑第一条长度 ≥ 500 字符的 system 消息包上 `cache_control: ephemeral`。system 提示词是整段对话里最稳定的部分，断点打在这里性价比最高。

**断点 2 — 历史尾部的 assistant 消息**
从倒数第二条往前扫，累计字符数 ≥ 2000 时，在遇到的第一条 **assistant** 消息上打断点。

三个设计取舍：

- **为什么打在历史尾部而不是开头**：这样每轮新消息进来，它前面的全部历史依然命中缓存，只有新增部分重新计费。缓存从"一次性"变成了"滚动"。
- **为什么选 assistant 不选 user**：assistant 消息是已完成、不会再被改写的；user 的最后一条永远是变量。
- **为什么要 2000 字符阈值**：上游缓存有最小长度要求（Claude Sonnet 约 1024 token），太短的断点不会生效，白占一个断点位。
  **注意这里用的是字符数不是 token 数**——中文约 2000 字符≈1400+ token，能过线；英文 2000 字符只有约 500 token，**过不了线**。这个阈值是按中文对话调的，英文场景需要调大（见第六节）。

### 附带的稳定性处理

真实客户端发来的请求经常不干净，网关顺手做了几件事：

- 过滤 `[Empty]` 污染消息（某些客户端在中断时会插入）
- 剥离容易引发 400 的 `tool_choice` 字段
- `max_tokens` 缺失时兜底
- 模型别名映射（上游模型下线时不必改客户端）
- 打印 `prompt_tokens_details`，**每次请求都能看到实际命中了多少** —— 调参全靠它

## 四、踩过的坑

**接入动态记忆库后，命中率从 90.6% 掉到 0。**

给这套链路接上一个会自动注入上下文的记忆系统之后，缓存命中率一夜归零。排查后定位到：记忆库每轮注入的 `live_context` 内容都在变化，而它被拼在 prompt 的**前部**——前缀一变，后面所有缓存全部失效。

这次故障暴露的是一条通用原则：

> **缓存友好的 prompt 结构，必须把"稳定的"放前面，"每轮都变的"放后面。**

顺序错了，再多断点也救不回来。修复方式是不再依赖客户端传来的 `cache_control`，改由网关自己识别稳定段并插入断点——也就是现在这份代码的做法。

## 六、已知局限（重要，请先读完再决定要不要用）

### 1. 默认是 5 分钟缓存；1 小时 TTL 可开，但要自己判断划不划算

默认发出的是 `{"type": "ephemeral"}`，即上游默认的 **5 分钟 TTL**：
**连续聊天时命中率极高，一旦离开超过 5 分钟，缓存整个失效。**

现已支持切换（`config.env` 里设 `CACHE_TTL=1h`），发出的是 `{"type": "ephemeral", "ttl": "1h"}`。
但 1 小时缓存的**写入价格是 2×**（5 分钟是 1.25×），所以并非无脑更优。

> ⚠️ **这条路径未经实测。** 上游文档声明支持该字段，但本项目从未用真实流量验证过它是否被正确透传、是否按 2× 计费。
> 启用前请自行小流量验证，不要直接上生产。

设同一段上下文在有效期内被复用 N 次，总写入+读取成本对比：

| 复用次数 | 5 分钟 TTL | 1 小时 TTL |
| --- | --- | --- |
| 1 次 | 1.25× | 2× |
| 2 次 | 2.5× | 2.1× |
| 3 次 | 3.75× | 2.2× |
| 5 次 | 6.25× | 2.4× |

**结论：一小时内只用一次，留 5m；会回来用第二次，就该切 1h。**

### 2. 缓存过期后的第一次请求，比不用缓存更贵

这是缓存机制本身的性质，不是本项目的 bug，但用之前必须知道：

| 情形 | 相对基础输入价 |
| --- | --- |
| 缓存命中（读） | ≈ 0.1× |
| 缓存写入（首次或过期后重建） | ≈ 1.25× |
| 不使用缓存 | 1× |

也就是说，**如果你的使用方式是"聊两句、走开半小时、再回来"，每次回来的第一条消息都要多付 25%**，而中间根本没攒够命中次数来摊平它。

**这套方案适合：** 高频、连续、长上下文的会话。
**这套方案不适合：** 低频、零散、每次都隔很久的调用——那种场景下它可能是负优化。

### 3. `allow_fallbacks: false` 是有代价的

锁死供应商换来了缓存一致性，代价是**上游限流或故障时请求直接失败**，没有备用通道。可用性换命中率，这个取舍要你自己判断是否接受。

### 4. 其他

- 只适配了 OpenRouter 的 `cache_control` 扩展，直连 Anthropic 原生 API 需要改写请求格式
- 断点数量固定为 2 个，未按上下文长度动态调整
- 命中率只打印到 stdout，没有落盘统计，无法做长期趋势分析
- 没有鉴权，**只应监听在内网或可信网络**
- **断点阈值按字符数而非 token 数计算**，跨语言不一致：2000 字符在中文下约 1400+ token（能触发缓存），在英文下只有约 500 token（**达不到最小可缓存长度，断点白打**）。英文场景需要把阈值调大到 4000 以上

### 5. 修过的两个 bug（保留在测试里）

- **累加器漏算结构化内容**：`content` 被上一轮打成 `[{"type":"text",...}]` 后长度按 0 计，断点会越打越靠前
- **结构化消息导致断点丢失**：当第一条满足阈值的 assistant 消息已是结构化内容时，早期版本直接 `break` 而不打断点，**历史断点整个消失、命中率砍半**，且日志上只表现为 `total breakpoints: 1`，极难察觉

两个都有对应的回归测试（`test_structured_*`）。

## 七、安全

- `config.env` 不随包分发，`.gitignore` 已排除
- 请求/响应落盘默认关闭（`DUMP_TRAFFIC=false`），因为其中含完整对话内容
