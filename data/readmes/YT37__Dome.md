# Dome

<p align="center"><img src="dome/ui/static/logo.svg" width="420" alt="Dome: Find the ring. Find the room."></p>

> **Find the ring. Find the room.**

**Live:** **[dome.surf](https://dome.surf)** (backup: [dome37.web.app](https://dome37.web.app)). It replays the recorded
real case; the Ask box answers live from the case files.

Dome is an investigation tool for trust and safety teams, anti-trafficking NGOs and police
trafficking units. Six agents under one LangChain **deepagents** supervisor pick out suspicious
social accounts, find the ring behind them, and narrow its photos down to the building, and the
room, where they were most likely taken. **Every output is a lead for human verification.**

**All data is synthetic.** No real accounts, people or phone numbers. Nothing is scraped.

**Ring A**: 12 posting accounts with a shared phone, a reworded ad script, reposted room photos
and three recruiters. Dome links them, draws the area, lists the buildings inside, matches the
photos to one building's scan, and explains a **High** lead.

## Run it

```bash
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"
pip install -r requirements-topo.txt   # optional: topological scorer (TopoModelX)
pip install "numpy>=2"                 # topomodelx 0.0.1 declares numpy<2; after installing requirements-topo.txt run: pip install 'numpy>=2' (needed by OpenCV 5; both work on numpy 2.5.4)
pytest -q
```

Copy `.env.example` to `.env` and add keys there (never in git). Every run uses all synthetic
layers (posts, messages, payments, the public ledger); Arlequin allows any synthetic data, so
no demo uses the public-only switch.

**The real case** (real CoStar, Matterport and Vexcel data tools; needs those keys and the
CoStar kit; about 2 minutes once cached):

```bash
DOME_STUBS=0 DOME_MONEY=1 DOME_SPOTTER=1 python -m dome.supervisor --case real-a --data synth --scripted
python -m dome.agents.briefer --case real-a --score data/answer_key/answer_key.json
python -m dome.eval_night
```

**Without data keys** (stub data tools, same agents and guards):

```bash
DOME_STUBS=1 python -m dome.supervisor --case synth-a --data synth --scripted
```

Drop `--scripted` to let the LLM supervisor plan the steps (`DOME_MODEL`, below). Outputs land in
`case/<case_id>/`: `rings.json` (with the money block), `spotter.json`, `zones.json`,
`candidates.json`, `matches.json`, `room_match.json`, `window_check.json`, `wallet_notes.json`,
`complex.json`, `brief.json`, `summary.html`, `events.jsonl` and the audit trail `log.jsonl`.

**Demo UI and replay:**

```bash
DOME_GLOBE=1 DOME_STEPS=1 DOME_ASK=1 python -m dome.ui.app --port 5001
```

then open `http://localhost:5001/?replay=demo-real-a` (the recorded real case). Replays in
`samples/demo_cases/` are written **only** with `python scripts/record_demo_case.py <case_id>
<demo_name>`: real runs carry CoStar street addresses internally, and the recorder blanks every
address field and refuses to save if one remains. The globe flight and the inside (360°/scan)
views need the local asset pack (`python -m dome.tools.demo_assets <scan_id>`, images in
`data/demo_assets/`), which is not in the repo; without it those views fall back to text.

**Flags** (environment variables, all off unless set):

| Flag | Effect |
|---|---|
| `DOME_STUBS` | `1` = scenario stubs for the data tools, `0` = real CoStar/Matterport/Vexcel (unset: real only if the keys are set) |
| `DOME_MONEY` | money discovery on the synthetic public ledger: wallet clusters, roles, flows, payment-then-post notes |
| `DOME_SPOTTER` | Spotter (agent 0): rule-based queue of accounts where 3+ signal kinds agree |
| `DOME_GRAPH` | UI runs live through the LangGraph server (`dome.graph_stream`) instead of the replay |
| `DOME_GRAPH_ASSISTANT` | LangGraph assistant for live runs; demo setting `dome_rules` |
| `DOME_GLOBE` | UI globe flight and inside view |
| `DOME_STEPS` | UI "Show the work" drawer (every agent's in-between results, read from real files) |
| `DOME_ASK` | UI "Ask about this case" box (answers only from the case files, with citations) |
| `DOME_MODEL` | LLM for the supervisor and Q&A, e.g. `google_genai:gemini-3.5-flash` (default), `anthropic:claude-sonnet-5-5`, `openai:gpt-5.5` |

Gemini answers (photo cues, window check, window fingerprint, Q&A) are cached under
`cache/gemini/`, keyed by model + prompt + images, so reruns make no new calls; if the quota
runs out and nothing is cached, W stays empty with "Gemini quota" as the reason.

**For developers:** the room match's in-between results (coarse ranking of every candidate
scan, the shortlist, inliers per photo and scan, room groups, P) are written to
`data/matches/summary.json` and copied per case to `case/<id>/room_match.json`; the complex and
the "Show the work" view read them from there.

| `synth` (784 accounts) | 1.00 | 1.00 | 1.00 | 150 accounts, all unlinked | 3 of 3 |

The scores cover every account in the dataset, hard negatives included. Each run also shows a reworded ad that

### Shared keyword

The same hashtag, emoji or code word (`#tapin`, the rose emoji for "roses" = money) used
again and again in captions and public comments (`comments.json`) is a sticky note (`keyword`,
weight 0.5, content layer). An account must use it at least twice, and a tag used by more than
40 accounts (`#love`, `#houston`) counts for nothing; a single use ("what does #tapin mean")
counts for nothing either. `python -m dome.synth.public_comments --data data/synth --key
data/answer_key/answer_key.json` plants the code words and the decoys. On synth: Ring A
plus its 3 recruiters form one ring, the friend group (heavy users of common tags) and the
one-off users stay unlinked, and content-only recall rises to 1.00.

### Messages and payments

Two more synthetic files, `messages.json` and `transactions.json`, sit next to the accounts
(`python -m dome.synth.private_layers --data data/synth --key data/answer_key/answer_key.json`
plants the patterns; `answer_key_private.json` scores them).

```bash
python -m dome.eval --data synth --three-way              # all layers on (the demo setting)
```

On `synth`, every planted pattern is found: shared wallet and DM links in Ring A, the relay
race (a burned phone moves from one account to the next, then that account's wallet moves on),
the three heartbeat accounts that take turns, 4 of 4 money-shape roles (collector, handler,
hub, recruiter) and echo events that join an ad, the buyer's message, the payment and the ride
inside 90 minutes. Hard negatives (friend group, rental hosts, busy motel, delivery driver)
stay unlinked.

| Layers | Precision | Recall | Hard negatives linked |
|---|---|---|---|
| content only | 0.99 | 1.00 | 2 |
| network only | 0.93 | 1.00 | 7 |
| both (Dome) | 1.00 | 1.00 | 0 |

Each layer alone links some hard negatives; requiring both is what keeps them out.

### Topological ring scorer

`dome/agents/topo.py` turns the Linker's evidence into a combinatorial complex: accounts are
points, every sticky note shared by 2+ accounts is one cell holding all of them (a phone, a
wallet, a DM thread, a heartbeat pair), and every echo event is a higher-order cell joining the
accounts of an ad, a message, a payment and a ride. A UniGCN hypergraph network (TopoModelX)
passes messages account → cell → account and outputs P(in a ring) per account. Each ring gets
`topo_score` (mean over members) as a second opinion next to the rule-based `confidence`; the
rules still make every link and write every reason.

```bash
pip install -r requirements-topo.txt            # optional; without it topo_score is null
python -m dome.agents.topo --train              # ~10 s on CPU, saves dome/models/topo_unigcn.pt
python -m dome.eval --data synth --three-way    # adds the four-way table
```

Trained only on `mini` Rings A and B (plus 70% of its other accounts). The mini Ring C row is from
Saturday's evaluation; the synth row was re-run on the final data:

| Test (never seen in training) | Precision | Recall | AUC |
|---|---|---|---|
| mini Ring C + 30% held-out accounts | 1.00 | 0.33 (2 of 6 above 0.5) | 1.00 |
| synth, whole dataset (account level) | 1.00 | 1.00 | 0.90 |

On synth, at the account level, the rule layers find 1.00 (content, precision 0.88), 0.80 (network,
precision 0.63) and 1.00 (both, precision 1.00) of ring accounts; the topological model scores
1.00 / 1.00 (AUC 0.90). On mini Ring C,
whose evidence looks different from A and B (no shared phone or script), every Ring C account
still ranks above every non-ring account (AUC 1.00), but only 2 of 6 clear 0.5: with this little
training data the model learns the shape of the rings it saw. `DOME_TOPO=0` turns it off.

**Public-only model (kept, not used in the demo; Saturday's numbers):** Arlequin allows any synthetic data, so every
demo runs with messages and payments on. A second model, `dome/models/topo_unigcn_public.pt`, was
trained without messages or payments for the public-only setting; on synth it still finds every
ring account (precision 1.00, recall 1.00, AUC 0.90); on mini Ring C every account still ranks
above every non-ring account (AUC 1.00) but none clears 0.5.

## Architecture

| # | Agent | Writes | Answers |
|---|---|---|---|
| 1 | Linker | `rings.json` | Which accounts are one ring, and why? |
| 2 | Zoner | `zones.json` | Where is the ring active, as an area? |
| 3 | Lister | `candidates.json` | Which buildings are inside and fit the photos? |
| 4 | Locator | `matches.json` | Which building's room and window view match? |
| 5 | Briefer | `brief.json` + `summary.html` | How strong is the lead and why? |

`dome/supervisor.py` is a `create_deep_agent` supervisor (`deepagents==0.7.38`) with three
specialist **sub-agents**, reached through Deep Agents' `task` tool:

| Sub-agent | Its tools | Job |
|---|---|---|
| `ring-analyst` | `run_linker` | Build the ring and say why (Spotter and money run with it) |
| `place-analyst` | `run_zoner`, `run_lister`, `run_locator` | Dome, buildings, room match, pin fix, window check |
| `brief-writer` | `run_briefer`, `write_brief_text` | Score from code, then the plain-language report |

All of them also have `case_status`, `log_decision` and read-only file tools (`ls`, `read_file`,
`glob`, `grep`) on the case folder through a Deep Agents `FilesystemBackend`. The supervisor itself
keeps only `case_status` and `log_decision`: it plans, checks `required_next` and delegates.
`execute`, `write_file`, `edit_file`, `delete` and the general-purpose sub-agent are not
registered, every write is denied by a `FilesystemPermission` that the sub-agents inherit, and a
harness profile hides the rest. `DOME_SUBAGENTS=0` falls back to a single supervisor.

One real Gemini-driven run of the case (`--case dag-a`, no `--scripted`) went supervisor →
ring-analyst → place-analyst → brief-writer and reached the same lead as the scripted run
(Building A, High 59, P 0.68, W 0.60). The brief-writer's first draft cited two numbers that are
not in that lead's factors; `write_brief_text` refused it, named them, and the second draft
passed. The run is recorded as the replay `demo-deep-agents`. A second run with LangSmith tracing
reached the same lead in 4 minutes; its public trace shows the three `task` calls, each specialist's
tools, the agents reading the case files (`read_file`, `glob`, `grep`; no writes) and the refused
draft: https://smith.langchain.com/public/ccdd3df0-49d8-4328-8a80-38f9b21f29d8/r/01a1df42-57b6-70a8-844c-21601db2bdde

The AI picks the next step, logs why, and writes the brief's words. **Numbers come from
deterministic code**: same case folder in, same scores out. Every `run_*` tool hashes its
inputs, validates the output against `dome/schemas.py`, retries once, then marks the step
failed.

**The supervisor is the Briefer's voice.** `run_briefer` computes the tier, score and caps.
The supervisor then calls `write_brief_text` with the plain-language reasons, what a human
should check next, and a case summary. That tool refuses any number not already in the
brief, a missing lead, a street address and any phone number, and never touches a tier or
score. `brief.json` records `text_source: "llm"` (or `"template"` with `--scripted`).

### Safety rules

Enforced in code, so they hold even if the AI forgets. Each writes a `decision` line to
`log.jsonl` with its evidence.

| Condition | Action |
|---|---|
| Ring confidence R < 0.4 | stop after the Zoner; the brief reports the area only |
| Zone is `wide` (city-wide clues) | the Lister keeps only buildings with a scan |
| No scan matches with P ≥ 0.4 | no building lead; the brief says so |
| No window in any photo | skip the window check (W = null), cap the lead at Medium |

Tiers: **High** needs P, W and R all ≥ 0.6. A strong room match (P ≥ 0.6) that falls short
anywhere else is **Medium**, with a cap line saying why. Everything else is **Low**.

## Guardrails

- Dome finds a building that matches the evidence. It does **not** prove anyone is inside.
- Place clues give an area (the dome), never an address. The brief shows a display name.
- A building needs a photo match to beat Low. High needs room **and** window match.
- The supervisor has no tool that contacts, dispatches or publishes anything. It stops at the brief.
- Every query, weight and decision is logged with a timestamp.
- Login and device layers are optional and off in the demo.

## The Linker

1. **Keys per account:** contact (phones, including disguised ones like "five5five 0142",
   @handles, $payment tags), photo (pHash; the photo id until real images exist), text (ad
   templates only, meaning posts with a contact or booking call-to-action: MinHash for copies
   plus `all-MiniLM-L6-v2` embeddings for rewordings), interaction (repeated reposts/replies, or
   amplifying the same post within an hour), place (area, landmark, area code), time
   (same creation day, lockstep posting). The device layer is off.
2. **Inverse-frequency down-weighting:** a key shared by many accounts counts for almost nothing.
3. **Two kinds make a link:** two accounts link only if they share two different kinds of key
   (place never counts toward the two). One kind alone is a weak hint, never a link.
4. **Layers must agree:** a cluster is a ring only if it has a content key and a connectivity
   key. Leiden splits linked groups of 20+.
5. **Recruiters:** a bio offering modelling or jobs, with most reposts/replies going into the ring.

6. **More sticky notes and patterns** (`dome/agents/patterns.py`): shared wallet (0.9), direct
   messages (0.85), same room from the Locator's room groups (0.8), same merchant (0.4, an
   area only, never counts toward the two), heartbeat (0.4: same daily rhythm, never active in
   the same 10 minutes), echo (0.7: two accounts in 2+ events). Relay race and money-shape
   roles are reported, not counted. `--layers content|network|both` (a public-only switch also exists; no demo uses it).

Ring confidence R = 1 − Π(1 − w_k) over the kinds the ring shares, capped at 0.95.

**Supervisor decisions:** a ring with roles but no place in its messages or payments makes
the Zoner fall back to login data and caps every lead at Medium; room groups holding photos
from accounts outside the ring re-run the Linker once with same-room links (logged with which
members and roles changed). The Lister adds up to +0.15 fit for buildings within 500 m of a
motel or echo place the ring paid; that reorders the list but never lifts a lead past Low.
Tuning lives in `dome/config.py`.

### Our work

- **The six agents and their contracts** (`dome/agents/`, `dome/schemas.py`, `dome/supervisor.py`):
