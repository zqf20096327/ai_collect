# LocalHarness

> Local agent harness for local LLMs (LM Studio / Ollama). Web UI on `127.0.0.1:7788`,
> tool use (shell, files, browser via CDP, multi-engine web search), goal mode with
> automatic context compaction, session history with Markdown export, Windows build via PyInstaller.
>
> **Quick start (Windows):** download `LocalHarness-Setup-v1.0.3.exe` from
> [Releases](https://github.com/lenovolquser15-ai/Local-AI-IDE/releases) (or use the portable zip),
> install LM Studio and load a model. The UI opens at `http://127.0.0.1:7788`.
> From source: Python 3.10+, deps from `requirements.txt`, `python -m harness serve`.
> Documentation below is in Russian.
>
> **Telegram-канал:** [t.me/RemingOstai](https://t.me/RemingOstai)

без кириллицы и пробелов — некоторые инструменты Windows их не любят.

## Запуск

| как | что делает |
|---|---|
| `LocalHarness-Setup-v1.0.3.exe` (из Releases) | установщик: без прав администратора, ярлык в меню Пуск, опциональный автозапуск; обновление и удаление не трогают `data` и `config.json` |
| `LocalHarness.exe` (после сборки) или `lh.cmd` | поднимает сервер на `127.0.0.1:7788` и открывает окно Chrome в режиме приложения |
| `python -m harness serve` | то же из исходников |
| `python -m harness cli "сделай X"` | разовый запрос в терминале |
| `python -m harness cli` | REPL (`/tools`, `/new`, `/stop`, `/exit`, `/goal <цель> == <критерий>`) |
| `python -m harness goal "<цель>" == "<критерий>"` | один цикл в режиме цели |
| `python -m harness check` | проверка: модель отвечает, dns-обход работает, список инструментов |
| `python -m harness wake` | попробовать поднять LM Studio |

Данные: `data\sessions\*.jsonl` (история), `data\shots\` (скриншоты), `data\jobs\` (фоновые логи),
конфиг — `config.json` рядом с кодом/экзешником.

## Что в интерфейсе

Окно разбито как в DeepSeek Harness: слева список сессий (сворачивается в рельс кнопкой ◧), по центру
лента прогона, справа панель «Траектория» с итогами хода. Поле ввода — с круглой оболочкой, внутри него
все переключатели, справа — кнопка отправки.

- **сессии** — название берётся из первого сообщения; поиск над списком фильтрует все сохранённые сессии по названию или ID, без ограничения последними 40;
- **переименование** — кнопка ✎ рядом с сессией открывает поле: Enter или ✓ сохраняет, Escape отменяет; пустые названия не принимаются;
- **экспорт** — кнопка ↓ скачивает Markdown с перепиской и вызовами инструментов; системный промпт и встроенные изображения не включаются. Перед публикацией проверь файл: сообщения и результаты инструментов могут содержать личные данные;
- **удаление сессий** — × открывает подтверждение внутри страницы. Выполняющуюся сессию удалить нельзя; после удаления открытой создаётся новая. Проверка: `python tests/live_session_delete.py`;
- **проверка модели** — предупреждение над чатом, если выбранная модель LM Studio не загружена либо её фактический контекст меньше заданного. Если CLI недоступен, проверка сообщает об этом, но не блокирует чат;
- **трей Windows** — собранное приложение остаётся в трее после закрытия окна; меню иконки открывает интерфейс или завершает сервер. `serve --tray` включает трей из исходников, `--background` не открывает браузер, `--no-tray` оставляет консоль, `LH_HEADLESS=1` отключает трей;
- **автозапуск** — флажок «Запускать с Windows» внизу боковой панели. По умолчанию выключен; использует HKCU Run для текущего пользователя, без прав администратора. Отключается тем же флажком;
- **провайдер / модель** — LM Studio (`127.0.0.1:1234/v1`) или Ollama (`11434/v1`);
- **набор инструментов** — `core` (базовые) и `full` (плюс окна, процессы, браузер через CDP, скачивание, lmstudio);
- **tools: auto / native / json** — как модель вызывает инструменты. `auto` один раз пробует нативный
  `tools`-протокол и, если локальная GGUF-модель его не тянет, переходит на JSON в тексте. Результат проб
  кэшируется в `data/protocol_cache.json`; кнопка «тест tools» перепроверяет;
- **права** — три положения (см. ниже);
- **⌁** — показывать/скрывать строку размышлений;
- **режим цели** + поле «критерий готовности», статус цели — полосой над полем ввода;
- **🖼 — прикрепить картинки**: кнопка в строке ввода, `Ctrl+V` и перетаскивание файла в поле тоже работают.
  Можно прикрепить несколько файлов (png/jpeg/webp/gif до 10 МБ) — над полем появляется лента превью,
  каждое можно убрать крестиком. Картинки уходят в модель вместе с текстом (см. «Картинки в чате»);
- **вкладки** — «Чат», «Плагины» (установка/отключение/каталог) и «LM Studio» (две плашки: «В памяти» и «На диске» + поиск/скачивание/импорт GGUF);
- **настройки** — шестерёнка в шапке открывает шторку: провайдер и модель, права, инструменты, параметры LM Studio, системный промпт. Внизу — ссылка «Нашли баг? Расскажите нам о нём →»: открывает GitHub Issues репозитория;
- **чеклист цели** — в режиме цели над полем ввода висит список пунктов с галочками; пункт «проверено» ставится, когда модель отчиталась по критерию;
- **плагины** — вкладка: включать/выключать, удалять, ставить из `plugins\catalog.json` или по прямой ссылке на `.py`; кнопка «перечитать папку» тоже есть;
- в шапке — `шагов · ток/с`, справа в панели — TPS, Output (токены), TTFT, Duration, Steps, ниже — лента действий;
- **шкала контекста** под шапкой — заполнение окна и засечка порога сжатия (см. «Шкала контекста и сжатие»).

## Картинки в чате

Кнопка 🖼 (а также `Ctrl+V` и drag&drop) прикрепляет файлы к запросу: в `POST /api/chat` уходит
`images` — список data-URL. Агент нормализует их (`harness/vision.py`), кладёт в сообщение как части
`{"type":"image_url"}` и отдаёт модели вместе с текстом; несколько картинок идут одним сообщением.

- Модель без vision получает только текст и честную пометку «изображений: N — модель без vision»;
- битая или слишком большая картинка не роняет прогон — в ленте появляется уведомление;
- текст можно не писать — тогда уходит «Посмотри на картинку»;
- `image` (одна картинка) по старому API продолжает работать: `images` — это просто список из одного элемента.

Живая проверка: `python tests/live_image.py` — рисует картинку, отправляет её в работающий харнес и
требует, чтобы модель её описала (`VERDICT: IMAGE OK`).

## Размышления модели

Reasoning-модели отвечают в двух каналах: отдельное поле `reasoning_content` (LM Studio, Qwen, DeepSeek-R1)
или inline-метки раздумий в самом тексте. Харнес разделяет их на лету:

- `reason` — живые куски раздумий (по 160 знаков или раз в 0.35 с), рисуются строкой «⌁ Глубокие раздумья»
  с shimmer-подсветкой; клик — развернуть текст;
- `thinking` — итог раздумий за ход, он же сохраняется в сессию и восстанавливается при открытии истории;
- в ответ (`delta`/`done`) раздумья не попадают: метки вырезаются `ThinkSplitter`/`strip_reasoning`,
  поэтому и в JSON-протоколе вызовы инструментов не ломаются текстом рассуждения;
- в CLI раздумья идут серым потоком, в конце — «‹размышление: N знаков›».

Транзиентные события (`delta`, `reason`, `speed`, `tool_start`) в `data\sessions\*.jsonl` не пишутся —
иначе лог раздувается на тысячу строк за один ответ.

## Права

| режим | поведение |
|---|---|
| `auto` (по умолчанию) | всё выполняется само, но чёрный список (`.SHELL_RULES` в `harness/permissions.py`: снос системных каталогов, `format`/`diskpart`, реестр/автозагрузка, отключение Defender, `net user`, `winsock reset`, force-push, `git reset --hard`, `curl \| sh`, запись в `C:\Windows`/`Program Files`, убийство системных процессов) выносит карточку «разрешить/запретить» |
| `unrestricted` | **вообще все права**: подтверждений нет, чёрный список отключён. Модель делает что хочет |
| `ask` | спрашивает перед каждым действием с побочными эффектами (`shell`, `write_file`, `edit_file`, `python`, `kill_process`, `download`, `lmstudio`) |

Отказ пользователя возвращается модели как наблюдение — она ищет другой путь, а не молча падает.

Отдельный стоп-лист (`HARD_BLOCK` в `harness/permissions.py`) действует **всегда, даже в `unrestricted`**:
`Restart-Computer`, `Stop-Computer`, `shutdown /r`, `wmic ... call reboot`, `netsh winsock reset`,
`bcdedit`, `format`/`diskpart`. Это команды, которые уносят машину: агент не имеет права перезагрузить
компьютер пользователя посреди работы. Модель получает отказ с объяснением и уходит в `web_fetch`/
`web_search`/другой инструмент; если без этого никак — может спросить пользователя через `ask_user`.

Причина блокировки не абстрактная: на живом прогоне модель, упёршись в недоступный Chrome, выполнила
`netsh winsock reset`, прочитала «нужен перезапуск компьютера» и выполнила `Restart-Computer -Force` —
машина ушла в перезагрузку. Теперь такой сценарий обрывается на уровне харнеса.

Ошибка браузера тоже стала actionable: если CDP недоступен, харнес пишет, что Chrome не запущен с
отладочным портом 9222, и прямо запрещает перезагружать компьютер или сбрасывать сеть, предлагая
вместо этого `web_fetch` по нужному адресу.

Слабая модель иногда вечно тыкает одной и той же упавшей командой (`list_dir("work")` → «не папка» → снова
`list_dir("work")`). Харнес считает повторы и **не убивает прогон молча** — вместо этого нарастает подсказка:

| повторов одной и той же упавшей команды | что получает модель |
|---|---|
| 2 | «ПОВТОР: возьми другие аргументы» (например абсолютный путь из сообщения об ошибке) |
| 3 | «ЗАЦИКЛИВАНИЕ»: повтор не сработает — найди решение или недостающие факты в интернете через `web_search`, затем `web_fetch` по найденной ссылке; попробуй другой инструмент или другой путь |
| 4 | «ТЫ СНОВА ПОВТОРЯЕШЬ ТО ЖЕ САМОЕ»: первым следующим действием вызови `web_search` |
| 5 | подход обрывается (в режиме цели — не прогон: подход начинается заново с другой тактикой) |

Три подряд упавших вызова (даже с разными аргументами) тоже дают подсказку «смени тактику, поищи в интернете».
Отказ пользователя и «цель не проверена» за зацикливание не считаются.

В режиме цели зацикливание больше не завершает прогон: подход обрывается, счётчики повторов обнуляются, а следующий
подход получает подсказку «ПРОШЛЫЙ ПОДХОД УШЁЛ В ПОВТОР НА <инструмент> — не повторяй его» и, со второго повтора,
прямое указание начать с `web_search` (в запрос подставляется тема цели). Тот же совет есть в системном промпте
и в инструкции режима цели — интернет для модели не ограничен.

Если и после этого прогреста нет (`goal_idle_limit` подходов подряд без единого успешного действия), срабатывает
предохранитель «нет прогресса» — честно, с подсказкой попробовать `web_search` вручную.

Повтор одного и того же `web_search` считается зацикливанием, даже если вызовы успешны: на третьем
одинаковом запросе модель получает подсказку «смени формулировку или укажи другой источник
(`engine=rightdao|wikipedia|bing|github|stackoverflow`)», на пятом подход обрывается. Раньше считались только
упавшие вызовы, и модель могла 15 раз подряд спросить одно и то же и получать один и тот же ответ.

## Глобальный поиск

`web_search` больше не привязан к одному поисковику. Модуль `harness/search.py` перебирает источники
и склеивает выдачу; если источник молчит (капча, «anomaly», пусто) — берёт следующий, а в ответе
отдаёт `sources` (кто ответил) и `errors` (кто и почему не ответил).

| источник | что это | доступен как |
|---|---|---|
| DuckDuckGo HTML | основной поисковик | `duckduckgo` |
| DuckDuckGo Lite | запасной, когда основной отдаёт «anomaly» | `ddg_lite` |
| Right Dao | независимый индекс, не режет по частоте запросов | `rightdao` |
| Bing | поисковик (адрес вытаскивается из редиректа `ck/a`) | `bing` |
| DuckDuckGo Instant Answer | короткий ответ и смежные темы | `ddg_ia` |
| Версии продуктов | endoflife.date: последняя версия и срок поддержки | `versions` (алиас `eol`) |
| Wikipedia ru/en | API, без капчи | `wikipedia` |
| StackOverflow | API | `stackexchange` (алиас `stackoverflow`) |
| GitHub | поиск репозиториев | `github` |
| Hacker News | Algolia API | `hackernews` |
| arXiv | Atom API | `arxiv` |
| npm / PyPI | реестры пакетов | `npm`, `pypi` |

Режим `auto` (по умолчанию, `search_engine` в `config.json`): сначала поисковики по очереди, пока не
наберётся нужное число ссылок; если выдача тонкая — добирают вертикальные базы. Конкретный источник
можно задать параметром `engine` — тогда молчит только он. Пустой результат честно объясняет, что
искать дальше, вместо тишины.

Отдельно ловится «anomaly»-страница DuckDuckGo: она выглядит как выдача, но внутри — фальшивые
ссылки (например, форма входа), и модель принимала их за результат. Теперь такая страница считается
отказом движка, а не выдачей, и цепочка auto уходит к следующему источнику.

Вторая защита — фильтр по теме. Поисковики с этого адреса иногда отдают совершенно чужие страницы
(Bing отвечал на «what is mit license» ссылками на форум Microsoft). Совпадение ищется по словам,
а не по подстроке, — иначе «mit» находилось внутри «Microsoft», а «лицензия» внутри «лицензионный»
из чужого сниппета. Заголовок и домен весят вдвое больше сниппета, поэтому «Активация Windows»
не проходит на одном случайном слове из описания. Результат, в котором нет ни одного значимого
слова запроса, отбрасывается; если не осталось ничего — движок считается не ответившим, и цепочка
идёт дальше. Среди уцелевших сначала идут те, где больше слов запроса.

Отдельный движок `versions` отвечает на вопрос «какая последняя версия Python / Node.js / Django»
по endoflife.date — точной цифрой, а не обсуждениями из выдачи.

Проверка: `python tests/test_search.py` (разбор выдачи, откат, дедуп, вертикали) и
`python tests/live_search.py` (живые запросы, печатает источники и ошибки).

## Зависания shell и ssh

Раньше прогон мог встать насмерть: `ssh` без ключа спрашивал пароль, и его приглашение уходило в консоль —
модель и харнес висели намертво. Теперь:

- `ssh`/`scp` запускаются с `BatchMode=yes` и `SSH_ASKPASS_REQUIRE=force` — пароль не спрашивается,
  неудача возвращается сразу (2–3 с вместо вечного ожидания);
- `shell` получает `stdin=DEVNULL`: команда, ждущая ввод (`cat`), не виснет;
- по таймауту убивается всё дерево процесса (`taskkill /T` на Windows), а не только сам процесс —
  иначе дочерний `ssh` держит пайп и `communicate()` не возвращается;
- если модель выдумала путь к ключу (`/home/.../.ssh/id_rsa`), харнес подставляет реальный ключ этой машины
  и пишет об этом заметку; если сервер ключ не принял — в ответе есть подсказка про `~/.ssh/authorized_keys`
  (пароль харнес не спрашивает и не подставляет).

Проверка: `python tests/test_images_and_hangs.py` (команда на stdin, таймаут с деревом, ssh без пароля).

## Параметры контекста LM Studio

`context_tokens` — лимит истории, которую LocalHarness отправляет модели после сжатия. Он не меняет уже загруженную модель. `lms_context_length` — длина контекста при следующей загрузке через `lms load`; после изменения параметра модель нужно выгрузить и загрузить заново. По умолчанию оба значения — `8192`.

Batch size и eval batch size — параметры backend/GGUF в LM Studio, а не параметры OpenAI-compatible запроса. LocalHarness не может надёжно изменить их через `/v1/chat/completions`; поэтому они остаются настройками LM Studio. В интерфейсе отображается и применяется только то, что поддерживает CLI: context length и TTL. Batch size и eval batch size берутся из профиля загрузки LM Studio; приложение их не перезаписывает.

## Шкала контекста и сжатие

Под шапкой висит тонкая шкала заполнения контекста: слева подпись вида `контекст 85% · 7k/8.2k токенов`,
справа — `сжатие при 7.3k ток · резерв 900`. На самой полосе стоит засечка — порог, на котором
начнётся сжатие; когда заполнение доходит до засечки, полоса меняет цвет на янтарный, при переполнении —
на красный. После сжатия в ленте появляется тонкая разделительная строка вида
`— контекст сжат: свёрнуто ходов — 4 —`.

Как считается:

- **вес истории** — не «знаки», а условные единицы: латиница и пунктуация ≈ 4 знака на токен
  (0.75 ед./знак), кириллица ≈ 2 знака на токен (1.6 ед./знак), картинки — фиксированная стоимость
  из `harness/vision.py`. Перевод в токены — деление на 3 (`UNITS_PER_TOKEN`); плоская оценка
  «3 знака на токен» врала в обе стороны.
- **постоянный резерв** вычитается из окна: схема инструментов (она уходит в каждом запросе)
  плюс `max_tokens` под ответ. Сжатие начинается не от полного окна, а от
  `context_tokens − (схема + резерв)`.
- **порог сжатия** на шкале — это `context_tokens − max_tokens`: после него история уже не влезает
  вместе с ответом, поэтому харнес сворачивает её сам.
- событие `context` шлётся перед каждым запросом к модели, в панели «Траектория» дублируется
  строкой `Context <использовано> / <окно> ток · сжатие при <порог>`.

Схема инструментов входит в каждый запрос, поэтому при профиле `full` на окне 8192 токенов сама
схема съедает ~5.7k — шкала сразу стартует около 70%. Если контекста мало, подними `context_tokens`
(и `lms_context_length`, чтобы LM Studio грузила модель с тем же окном) или переключи набор
инструментов на `core`.

## Системный промпт и модели

На вкладке **LM Studio** появился редактор «Системный промпт». Текст сохраняется в `config.json` и добавляется к базовым правилам LocalHarness для новых запусков. Не удаляй из пользовательского текста указания про проверку результата, права и SSH-реквизиты.

Модели можно скачивать через поле на вкладке LM Studio: введи идентификатор, который поддерживает установленный `lms.exe`, например `qwen/qwen3-4b-instruct`, и нажми «Скачать». Прямой Hugging Face URL сам по себе не всегда является форматом LM Studio; для GGUF используй поддерживаемый `lms get` идентификатор или скачай файл через инструмент `download`, после чего загрузи его через LM Studio.

## Режим цели и остановка

В режиме цели события reasoning теперь отправляются чаще: они появляются примерно каждые 80 знаков или 0,12 секунды, а не только после крупного буфера. Это уменьшает ощущаемую задержку при длинном VPS-прогоне. Если модель не присылает reasoning-канал, UI всё равно показывает план/вызовы инструментов — локальная GGUF-модель может не поддерживать отдельный канал размышлений.

Кнопка «Остановить» сразу выставляет stop-флаг и закрывает активный HTTP-поток к LM Studio/Ollama, поэтому не ждёт завершения генерации. После остановки новый запрос можно отправить в той же сессии.


Отмечен «режим цели» → харнес не останавливается на первом тексте ответа:

1. модель работает, пока сама не вызовет `finish_goal(achieved, summary, evidence)`;
2. ответила без `finish_goal` → считается незакрытой, харнес добавляет подходы
   и заставляет проверять и доделывать;
3. `goal_rounds` в `config.json` задаёт потолок подходов: **`0` = бесконечно**,
   положительное число — жёсткий лимит (по умолчанию `6`), после которого в лог попадает `цель не закрыта`;
4. каждый подход получает свежий бюджет `max_steps` (раньше бюджет был общим и после исчерпания
   подход получал лишь 1 шаг — отсюда «за N шагов не дала ответа»).

В бесконечном режиме (`goal_rounds: 0`) прогон останавливают только: `finish_goal`, кнопка «Остановить»,
срыв по 3×-повтору одной упавшей команды, либо предохранитель холостого хода — если `goal_idle_limit`
(по умолчанию 4) подходов подряд модель не вызвала ни одного реального инструмента и не закрыла цель
(застряла на болтовне). Это не мешает нормальной долгой работе: там инструменты вызываются каждый подход.

Сжатие контекста (`fold`/`fold_hard`) больше не роняет прогон на jinja-400 `roles must alternate`:
перед каждым запросом `normalize_messages` приводит историю к строгому чередованию user/assistant
под шаблон Ministral (assistant с `tool_calls` и tool-результаты «прозрачны»), склеивает соседние
одноимённые роли и привязывает осиротевшие tool-результаты. Проверено повтором проверки из GGUF-шаблона.

Жёсткое сжатие `fold_hard` сохраняет память о последних шагах даже при десятках сжатий подряд:
старые дайджесты не копятся, а сворачиваются в один новый, а под бюджет урезается содержимое
сообщений, а не сами сообщения — самое свежее наблюдение или напоминание о цели остаётся последним
всегда. Раньше при накоплении дайджестов цикл урезания выбрасывал свежий хвост, последним сообщением
навсегда оставалась исходная задача, и модель в режиме цели начинала бесконечно повторять одно
и то же действие. Проверка: `python tests/test_context.py` (12 раундов повторного сжатия)
и живой прогон `python tests/live_goal_proof.py`.

Критерий готовности из UI попадает в постановку цели — формулируй его проверяемо
(«`python -m harness check` печатает OK», а не «чтобы работало»).

## Сбитый формат ответа

Локальная модель иногда вместо ответа переписывает наблюдения инструментов (`user: [web_search] -> …`)
или не отвечает вовсе. Раньше такой ход просто закрывал прогон пустым ответом. Теперь харнес
замечает сбой, показывает модели её собственный последний ответ и говорит нужный формат:

- JSON-протокол: ровно один объект `{"tool":"<имя>","args":{…}}` либо `{"final":"<ответ>"}`;
- нативный протокол: сразу готовый текст ответа.

На это даётся до двух попыток (`FORMAT_RETRIES`), каждая — отдельный шаг с лимитом. Если модель
и после этого не ответила — прогон завершается, но не молча: в лог и в UI уходит причина.

Проверка: `python tests/test_format_retry.py` (три сценария: эхо наблюдений, пустой ответ,
эхо в нативном протоколе).

## Плагины

Положил `.py` в папку `plugins` проекта → нажал «плагины» → инструменты видны модели в том же списке.

```python
NAME = "example"

def do_it(cfg, args):
    return {"ok": True, "value": args.get("x")}

TOOLS = [{
    "name": "do_it",
    "desc": "что делает, по-русски и коротко",
    "params": {"x": ("number", "зачем")},
    "required": ["x"],
    "dangerous": False,   # True -> вызов всегда выносится на подтверждение в режиме auto
    "fn": do_it,
}]
```

Файл с синтаксической ошибкой не роняет харнес: карточка на вкладке «Плагины» показывает ошибку.
Пример в репозитории: `plugins\waitfor.py` (`sleep`, `wait_port`). Каталог: `plugins\catalog.json`
(waitfor, netprobe, notes) — «Установить» копирует шаблон из `plugins\_templates` или качает по `url`.
Свой источник каталога: `config.json → plugin_catalog_url` (JSON со списком записей).

## Git

Модель умеет работать с репозиторием инструментом `git`: `status` (изменения и ветка), `diff`
(`staged`, `stat`), `log`, `show`, `add` (`path` или `all`), `commit` (`message`), `branch`
(список, переключение или создание по `name`). Команды собираются массивом аргументов, без шелла,
поэтому кавычки и кириллица в путях не ломаются; `quotepath` выключен, чтобы имена файлов читались.

Сеть (`push`, `pull`, `fetch`) в инструмент намеренно не входит: это действия наружу и с чужим
состоянием, их модель делает только по явной просьбе через `shell`. `git add -A` разрешён только
из корня репозитория — иначе один вызов из подпапки затянул бы в коммит весь проект.
Ошибки переведены на язык пользователя (не репозиторий, не настроен автор, нечего коммитить)
и подсказывают следующий шаг. Проверка: `python tests/test_git_tools.py`.

## LM Studio: две плашки

Вкладка «LM Studio» разбита на две карточки, как просили:

- **«В памяти»** — `lms ps --json`: что загружено, контекст, квант, размер, кнопка «выгрузить»;
- **«На диске»** — `lms ls --json`: скачанные модели, кнопка «Загрузить» (контекст и TTL берутся из полей над списком),
  поиск/скачивание (`lms get <имя> --gguf -y`) и импорт локального GGUF (`lms import`).

Скачивание идёт фоном; лог — под полем поиска. Сеть LM Studio должна сама достучаться до хаба
(если хаб не отвечает — качай через браузер/торрент и импортируй файл).

## Обучение и дообучение моделей

Да, LocalHarness может помогать **подготовить и запустить** обучение, но LM Studio сам по себе обычно используется для инференса, а не для fine-tuning. Добавлены инструменты:

- `dataset_append` — добавляет примеры `instruction/input/output` в JSONL;
- `dataset_validate` — проверяет JSONL и считает битые строки;
- `model_info` — показывает доступные модели провайдера;
- `train_model` — запускает внешний LoRA/SFT-тренер в фоне через PowerShell.

Для реального обучения нужен установленный тренер и GPU/VRAM, например LLaMA-Factory, TRL/PEFT, Axolotl или другой совместимый стек. LocalHarness не делает вид, что обучил модель: цель закрывается только после проверки лога тренера и появления выходного adapter/checkpoint. Пример команды нужно подставлять под установленный стек; не запускай обучение наугад.

Важно различать:

- **память/заметки** — модель не меняется;
- **RAG/датасет** — модель не меняется, данные подаются при запросе;
- **LoRA/QLoRA fine-tuning** — создаётся adapter, который затем нужно подключить к модели;
- **полное обучение** — требует значительно больше VRAM/времени и не выполняется через LM Studio API.


В конфиге по умолчанию включён профиль `full`: модель видит все встроенные инструменты — PowerShell, SSH к VPS, файлы, поиск/загрузку, Python, окна и скриншоты, браузер через CDP, процессы, системную информацию, фоновые задачи, буфер обмена, LM Studio, плагины и долговременные заметки.

PowerShell можно вызвать явно инструментом `powershell` или обычным `shell` (он уже запускается через PowerShell). Для VPS используется установленный в Windows OpenSSH-клиент и ключ/ssh-agent — пароли в конфиг не сохраняются:

```json
{
  "ssh_profile": "my-vps",
  "ssh_profiles": {
    "my-vps": {
      "host": "203.0.113.10",
      "user": "root",
      "port": 22,
      "key": "C:/Users/<user>/.ssh/id_ed25519"
    }
  }
}
```

После этого модель может вызвать `ssh(command="uname -a", profile="my-vps")`, а для разовой проверки — передать `host`, `user`, `port` и `key` прямо в вызове. Установка файлов на VPS выполняется обычными командами `scp`/`rsync` через `shell` или через `ssh` с heredoc/командой на сервере. Если SSH не подключается, сначала проверь вручную в PowerShell: `ssh -vvv -i <key> <user>@<host>`; частые причины — закрытый порт 22, неверный пользователь, ключ с неправильными правами или отсутствие записи в `known_hosts`.

По умолчанию опасные локальные и удалённые действия проходят через подтверждение в режиме `auto`; это не ограничение возможностей, а защита от случайного удаления, остановки сервисов или перезаписи файлов. `unrestricted` отключает подтверждения, но использовать его стоит только в изолированной среде.


Если в системе сломано разрешение имён (`getaddrinfo` падает для всех внешних имён), `curl`/`requests`
по доменам не едут. `harness/dnsfix.py` резолвит сам (dnspython → `Resolve-DnsName -Server` → `nslookup`, кэш в
`data/dns_cache.json`) и соединяется по IP с настоящим SNI, так что сертификат проверяется как обычно.
Модель выходит в сеть только через `web_search`, `web_fetch`, `download`.

## Скорость генерации

`speed`-событие считается по ходу стрима: время до первого токена, токены (из `usage`, если сервер его
присылает, иначе оценка ~3.6 знака на токен — для кириллицы и Qwen-токенизатора) и ток/с.
Оценка помечена как оценка, точные числа приходят с `usage`.

## Сборка .exe

Установи зависимости и сборщик, затем запусти безопасный сценарий из корня проекта:

```
python -m pip install -r requirements.txt pyinstaller
build-exe.cmd
```

Результат: `dist\LocalHarness\LocalHarness.exe`. Сборка сначала создаётся в отдельной папке `.stage-*`;
установленный экземпляр не затрагивается при ошибке. Перед заменой закрывай приложение через меню трея.
Сценарий переносит копии `data`, `work`, плагинов и конфига старой сборки в новую, а старую целиком
оставляет в `dist\.previous-*` как резервную копию. Для отдельной тестовой сборки можно задать `LH_BUILD_DIST`.
Не запускай PyInstaller напрямую поверх папки с живой историей: он удаляет каталог onedir.

Свежая сборка без старого экземпляра использует безопасные значения по умолчанию и не копирует личный
корневой `config.json`. Данные создаются рядом с exe; `LH_DATA` и `LH_CONFIG` позволяют выбрать другие пути.
Перед публикацией сборки проверь отсутствие личных `data`, `work`, `config.json` и установленных сторонних плагинов.

### Установщик

Из чистой релизной сборки собирается Inno Setup-установщик (`installer.iss`):

```
LH_BUILD_DIST=dist/release build-exe.cmd
build-installer.cmd
```

Результат: `dist\LocalHarness-Setup-v<версия>.exe`. Установка per-user в `%LOCALAPPDATA%\Programs\LocalHarness`,
без прав администратора. Автозапуск (опциональный флажок) пишет HKCU Run в том же формате, что и флажок
в интерфейсе, — они совместимы. При обновлении и удалении пользовательские `data`, `work` и `config.json`
остаются на месте. Перед установкой поверх работающей версии закрой приложение через меню трея.

## Разбудить модель

`lms.exe server start` поднимает сервер LM Studio без кликов по GUI, `lms load <модель>` загружает модель
в память — харнес делает и то и другое сам (кнопка «разбудить», `lh wake`, автопроверка при старте).
Пути к `LM Studio.exe` и `lms.exe` лежат в `config.json` (`providers.lmstudio.exe` / `.lms_cli`).

## Известные ограничения

- Модель по умолчанию текстовая: скриншоты сохраняются и показываются в UI, но сама модель их не видит.
  Если модель умеет vision (например, `ministral-3-*`), картинки из чата и скриншоты доходят до неё — харнес
  определяет это по флагу `vision` в конфиге и по имени модели.
- `browser` работает только если Chrome запущен с `--remote-debugging-port=9222`.
- Если LM Studio вообще не установлена и `lms.exe` нет — «разбудить» не сможет, UI честно напишет «не отвечает».
- Нативные `tools` у локальных reasoning-моделей часто не работают — для этого и есть `tools: json`.
- В собранном `.exe` инструмент `python` поднимает REPL не на `sys.executable` (это сам харнес), а на настоящий
  интерпретатор из `PATH` (`python`/`python3`/`py`) или из переменной окружения `LH_PYTHON`. Python с машины
  убрать — и инструмент честно ответит «нет интерпретатора», не роняя прогон.
