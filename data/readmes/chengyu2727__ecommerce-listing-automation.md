# ecommerce-listing-automation · 电商商品自动化上架系统

> **一句话总结**：把「多 SKU × 多平台上架」从**手工填表**变成**数据驱动的一条命令** ——
> Python 负责清洗 / 生成 / 校验，AI Agent 负责标题与合规，影刀 RPA 负责点浏览器，人只做最后复核。

`Python 3.10+` · `pandas / openpyxl / Pillow` · `影刀 RPA` · `LLM(OpenAI 兼容，可选)` · `pytest 51 passed`

![后台自动填表演示](docs/screenshots/demo_tmall.gif)

> 上图由 `tools/make_demo_gif.py` 读取**真实任务包**（`outputs/rpa_tasks/tmall_tasks.json`）逐帧渲染，
> 不是录屏、不是手画。**是 `config/platforms.json` 里 `publish_flow` 定的** ——
> 和任务包 `steps`、和商家在后台真实点击的顺序三者同源。天猫这里走 9 屏：
>
> 入口（商品 → 发布宝贝 → 一口价）→ **选类目（搜索 + 选路径，选定不可改）** → 主图（图片空间选 5 张）
> → 标题 + **品牌** + 卖点 → **商品属性（下拉枚举，红星必填）** → **SKU 表（勾选规格 → 生成行 → 逐行填价/库存/编码）**
> → 条码 + 物流服务 → 详情 + 资质上传 → 提交审核。
>
> 换 `--platform jd` 会变成京东真实顺序（类目 → 名称 → 属性 → 销售属性 → 图片 → 介绍 → 物流 → 资质 → 提交），
> 换 `--platform douyin` 又是另一套（类目 → 品牌 → 名称 → 主图 → 规格库存 → 物流 → 详情 → 资质 → 提交审核），
> 因为顺序读的是配置，不是代码。逐平台对账见 **[docs/平台实操对照.md](docs/平台实操对照.md)**。

## 项目背景

这个项目来自一段真实的电商运营实习：一家**以代销为主的电商公司**，
品牌方/工厂供货、公司负责线上销售（不压货或少量压货），团队规模很小、一人多职。
我在里面做运营 + 采购，实际承担"后端执行 + 前端商务谈判助理"的双角色：
一边把品牌方给的资料变成四个平台能上架的商品，一边参与选品沟通与渠道对接。

主营品类是**燕窝线**（干燕盏、燕条、即食、鲜炖、燕窝粥、节令礼盒），
另外搭配阿胶、花胶、银耳羹、蜂蜜这类滋补食品 —— 一个主品类打底、不全押在一个品类上，
这是代销公司常见的选品结构。

**场景里的三个硬约束，直接决定了这个项目的形态：**

| 场景特征 | 对上架工作的影响 | 项目的应对 |
| --- | --- | --- |
| 代销不压货，SKU 换得勤、单批量小 | 上架是"高频小批量"，堆时间没用，只能提高单位时间产出 | 主流程做成"一条命令跑完"，不搞一堆前置模板配置 |
| 淘宝 + 天猫双店同款 | 同款要上两次，字段名几乎一样但**规则不同**（品牌授权、类目资质、标题规范），复制过去会被打回 | 平台差异全部配置化，两个平台各自一套规则 |
| 没有专职文案/美工/资质专员 | 标题、详情、图片都得自己搞；燕窝还是强监管品类（溯源、检疫、资质） | AI 生成标题 + 图片批处理 + 资质/溯源字段前置校验 |

再叠加品类特性：**燕窝属普通食品，不能宣称任何保健或治疗功效**，
"美容养颜""增强免疫力""孕妇必备"这类词是下架重灾区；进口燕窝还要报关单、检疫证明、溯源码。
这些不是"通用电商规则"，是品类知识 —— 所以规则层被拆成了**平台**和**品类**两个维度。

### 平台商品上架的痛点

36 个 SKU × 4 个平台 = **144 次上架**，每次都是同一份信息按不同规矩重写一遍：

| 痛点 | 具体表现 | 代价 |
| --- | --- | --- |
| 多平台重复操作 | 淘宝 / 天猫 / 京东 / 抖音四个后台，字段名不同、逻辑相同 | 时间耗在同一套动作上 |
| 双店同款 | 天猫要品牌授权、类目资质、条码，淘宝不要；直接复制就被驳回 | 复制过去等于白填 |
| 标题规则各异 | 字数上限、关键词偏好、违规词表都不同，还叠加品类禁词 | 写完逐条改，容易踩雷降权 |
| 详情页重复填写 | 参数/卖点/规格要跨平台复制并适配格式 | 同一份信息填 4 遍 |
| 人工成本高 | 单 SKU 上 4 平台约 2-3 小时，机械操作占大头 | 一天最多推进 3-4 个 SKU |
| 出错率高 | 漏填溯源码、错填类目、主图尺寸不合格 | 提交被驳回 → 返工 → 更慢 |
| 资料散乱 | 品牌方资料散在微信、报价单、随手拍图里，规格写法不统一 | 上架前先花时间"把资料读明白" |

这些环节的共同点是：**它们全都是规则，而规则就该写成代码。**

## 核心判断

> 电商商品上架的本质是「**结构化数据录入 + 平台适配**」。
> 能被规则描述的部分（字段映射、字数、禁词、图片规格、类目路径）交给代码；
> 需要判断的部分（标题措辞、卖点归纳）交给模型，但要用规则约束住；
> 需要点鼠标的部分（后台表单）交给 RPA。
> **人只保留"复核"这一件事。**

一句补充：这条判断的价值不在"省了几个小时"，而在**可复制**——
规则写下来之后，新人上手、换平台、加品类，都不再依赖某个人的记忆。

## 系统总览

```
  品牌方资料 ──▶ ① 数据清洗       列名归一 / 价格清洗 / 类目映射 / 品类识别
  Excel·微信·报价单    │           ↓ 输出 sku_master（单一数据源）
                       ▼
  商品图片   ──▶ ② 图片处理       改名 / 校验 / 压缩补白（源图不够不放大）
                       │
                       ▼
              ┌──────────────────────────────────────────────┐
              │ ③ AI Agent 层                                 │
              │   title_generator ── 平台规则 + 品类风格 + 打分  │
              │   compliance_check ─ 平台禁词 + 品类禁词 + 字段  │
              │   info_extractor ─── 正则管数字 / LLM 管语义     │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ ④ 平台适配   platforms.json（后台怎么填）      │
              │              categories.json（品类要多填什么） │
              └───────────────────┬──────────────────────────┘
                                  ▼
              ┌──────────────────────────────────────────────┐
              │ ⑤ 任务编译   payload = {控件中文名: 值}        │
              └───────────────────┬──────────────────────────┘
                                  ▼
   影刀 RPA ◀── 登录 → 进发布页 → 选类目 → 填标题/属性/价格 → 传图 → 提交 → 截图
```

**四个设计取舍：**

1. **规则和代码分开**：平台差异在 `platforms.json`，品类差异在 `categories.json`，主流程只读配置。
2. **AI 是加速器，不是地基**：每个 AI 模块都有模板/正则兜底。没有 Key、断网、模型超时，流水线照样跑完。
3. **Python 不碰浏览器**：只产出「控件中文名 → 值」的契约，影刀按名字定位控件。平台改版只改流程，不动数据侧。
4. **数据只有一份**：所有平台适配都从 `sku_master` 出发，不允许多份 Excel 各填各的。

## 两条边界：规则从哪来、程序到底动谁

这两件事如果不说清楚，整个项目就是"看起来很像"的假 demo。所以放在最前面讲。

### ① 规则不是逐平台检索官方工具得出的，而是"后台可见字段 + 公示规范 + 品类经验"

`platforms.json` 里的字数上限、必填项、图片规格、禁词表、控件中文名，来源是三块：

| 来源 | 具体拿到什么 | 可信度 |
| --- | --- | --- |
| 各平台商家后台「发布商品」页面本身 | 字段名、哪些带必填星号、类目选择器长什么样、标题输入框的字数提示、各步骤的先后 | 最硬 —— 后台写什么，`publish_flow` 与 `form_labels_extra` 就写什么 |
| 平台公示的发布规范 / 违规处罚规则 | 标题字数区间、绝对化用语、类目资质要求、"属性需与标题一致"这类审核口径 | 较硬，但会随规则更新 |
| 燕窝品类的监管与抽检口径 | 普通食品不得宣称功效、进口需报关单与检疫证明、溯源码可查 | 品类知识，不是平台知识 |

**没做的事**：没有把任何平台的规则文档抓下来做全量比对，也没有对**商家工作台/数据工具**（生意参谋、京麦、抖店罗盘这类）做接口级调研。所以这套规则应当被理解为"够用的初版"，不是"平台口径汇编"—— 版本号 `2.0.0`、全部集中在两个 JSON 里，就是为了能人工复核和快速修订（见文末「局限与边界」）。

顺带纠正一个常见误解：**生意参谋是淘宝的数据/流量分析工具，京麦是京东的商家工作台（订单、客服、营销），它们都不是"商品发布 API"。** 上架这件动作，落到最后还是各平台自己的「发布商品」页 / 类目发布接口。

### ② 程序走的就是浏览器里的商家后台，不接任何开放平台 API

```
Python  ──►  任务包 + 步骤契约（JSON）
                     │
                     ▼
影刀 RPA  ──►  打开 sell.tmall.com/publish.htm（platforms.json 的 publish_url）
              登录 → 选类目 → 填标题/属性/价格库存 → 传主图 → 提交 → 截图
                     ▲
                     └── 和运营手工操作的，是同一个界面
```

| 走法 | 本项目 | 说明 |
| --- | --- | --- |
| 浏览器操作商家后台发布页 | ✅ 就是这条路 | 任何商家账号能登录就能跑；代价是平台改版要改流程、登录要人工过验证码 |
| 平台开放平台 API（商品发布接口） | ❌ 不接 | 淘宝开放平台 / 京东宙斯 / 抖店开放平台需要企业资质与开发者审核，个人作品集拿不到 |
| 商家工作台 / 数据工具（生意参谋、京麦） | ❌ 不接 | 它们没有"发布商品"的开放接口，接进去也发不了商品 |
| 平台自带批量导入（Excel/CSV 模板） | ❌ 没做 | 类目支持时它其实比 RPA 更稳（见下一节对比），但字段各平台不同、部分类目不支持 |

**为什么选这条路**：与手工操作同一界面，就不会被 API 权限和资质卡住 —— 这也是小代销团队唯一能落地的路子。代价很明确：**脆弱**（DOM 改版即失效）和**必须保留人工登录**。如果哪天拿到企业资质，最自然的升级是把最后一环从"浏览器填表"换成"调用发布接口"，前面的 `sku_master`、规则层、任务包一行都不用改 —— 这就是执行层被做成一个薄适配器的原因。

## 和真实后台对账：四个平台的流程差在哪

第一版的任务包和演示图是**照我自己写的代码顺序排的**，不是照后台排的：一条任务固定 10 步，类目当文本框填，属性当键值对塞，没有 SKU 表、没有物流、没有资质。
后来拿千牛上架实操视频和四家后台的公开字段说明逐项对了一遍，差得挺远。这一节记的就是对账结果，完整版在 **[docs/平台实操对照.md](docs/平台实操对照.md)**。

### 四个平台的字段顺序不一样，而且不是"随便不一样"

| | 淘宝（千牛） | 天猫 | 京东（京麦） | 抖店 |
| --- | --- | --- | --- | --- |
| 类目 | 选择器，选完锁定 | 同 | 同 | 同（叫"商品类目"） |
| 品牌 | 属性里填 | **独立必填阶段** | 基础信息里填 | **独立必填阶段** |
| 名称 | 商品标题 ≤30 汉字 | 同 | **商品名称 ≤50 字 + 商品标语 ≤45 字**（两栏） | 商品名称 ≤30 汉字 |
| 规格 | SKU 表 | SKU 表 | **叫"销售属性"**，勾完规格才生成行 | **叫"规格与库存"** |
| 图片位置 | 标题之后 | 同 | **标题和属性之后** | 名称之后 |
| 条码 | 有，可勾"我没有条形码" | 同 | 基础信息里 | 无独立阶段 |
| 详情 vs 物流 | 物流 → 详情 → 资质 | 同 | **介绍 → 物流 → 资质**（详情在前） | 物流 → 详情 → 资质 |
| 提交 | 提交 | 提交（品牌审核更严） | 提交 | **提交审核**（1–24h） |

顺序不是先后审美问题：**类目一变，后面能填的属性、能传的图片尺寸、能选的运费模板全部跟着变**，
所以流程引擎里第一步就是类目，且标记 `immutable` —— 选错只能重开一张单。

## 模块说明

### ① 数据清洗 `src/data_processing/excel_convert.py`

**解决**：表头五花八门、价格带 `￥`、卖点用 `;；、|` 混排、参数是一坨 `key:value` 文本、类目写的是口语。

- **列名别名映射**：20+ 种表头写法 → 13 个标准字段，认不出的列单独列出（不静默丢弃）
- **字段解析**：`￥1288.00元 → 1288.0`、`产地:印尼;盏型:4A燕盏;净含量:50g → dict`
- **类目映射**：`即食燕窝 → 食品/保健食品/膳食营养补充食品 > 燕窝 > 即食燕窝`，
  模糊匹配且**长键优先**（否则"燕窝"会把"即食燕窝"抢先命中）
- **品类识别**：输出 `category_key`（birdnest / tonic / food），后续所有品类规则都靠它
- **SKU 编码**：`前缀-型号`（`DEMO-YW4A50`），与仓库/工厂口径一致，不另建主键
- **质量校验**：缺库存/价格异常/缺条码/类目未匹配/卖点为空 → error / warn 两级落盘

```python
from src.data_processing.excel_convert import load_raw, convert_dataframe, write_outputs

result = convert_dataframe(load_raw("data/raw/品牌方商品清单.xlsx"))
print(result.stats)      # {'总行数': 36, '有效SKU': 36, '错误数': 1, '告警数': 4, ...}
write_outputs(result)    # sku_master.csv / .xlsx / .json + data_issues.csv
```

### ①b 字段补全 `src/data_processing/enrich.py`

**解决**：商家自己的表只有六列，卖点和参数全在老板脑子里 —— 系统不能凭空变出来，但能把名字里的信息先榨干。

- **属性反解**：`印尼干燕盏 4A 50g` → 产地 / 盏型 / 等级 / 净含量；`70g*6瓶` 这类纯度量值直接当净含量
- **已有值优先**：表里写了的字段不被名字覆盖，品牌方的原话要保留
- **来源留痕**：反解出来的字段记在 `specs_derived`，返回 `input_level`（full / partial / basic）
- **待办产出**：`data/processed/enrich_log.md` 直接写"这个 SKU 该补什么、找谁要"

```bash
$ python -m src.data_processing.enrich --sku data/processed/sku_master.json
{
  "记录数": 8,
  "反解字段数": 28,
  "被反解的SKU": 8,
  "输入完整度": {"full": 0, "partial": 8, "basic": 0}
}
```

**边界**：只抄不猜。溯源码 / 保质期 / 储存条件 / 条码不生成 —— 这类字段编出来比空着更危险。

### ② 图片处理 `src/data_processing/image_process.py`

**解决**：主图尺寸不够被驳回、图片超体积传不上去、文件名乱导致"第 3 张传到第 1 张的位置"。

- **校验**：按平台规则检查最短边（淘宝/天猫/京东 800、抖音 600）、宽高比、体积上限、格式
- **修复**（`--fix`）：等比缩放 + 白底补方 + 质量递降压缩；**源图不够大不放大**（放大只会更糊，仍判低质）
- **改名**：`<sku>_main_01.jpg` / `<sku>_detail_02.jpg` —— RPA 按文件名顺序上传，天然不会错位

```json
{"sku_id": "DEMO-XDZ7",
 "platforms": {"tmall": {"pass": false,
   "issues": ["DEMO-XDZ7_main_01.jpg: 最短边 400px < 平台要求 800px（400x400）"]}}}
```

### ③ 标题生成 `src/ai_agent/title_generator.py`

**解决**：同一个商品，四个平台不该是同一句话。

- **核心词前置**：前 12 字权重最高，品类词放最前
- **品类属性词**：取哪几个属性由 `categories.json` 的 `spec_order` 决定（燕窝是产地/盏型/净含量/干度/唾液酸），
  平台只决定"取几个"；`title_skip` 把不该进标题的属性排除（配料表、储存方式、保质期属于详情页）
- **值不自解释就带标签**：`唾液酸：≥10%` 不会在标题里蹦出一个孤零零的 `≥10%`，会拼成 `唾液酸≥10%`；`50g` 这种则保持原样
- **场景词按品类**：燕窝给"日常滋养 / 长辈送礼 / 年货礼盒"，不会出现"办公 / 车载"这种外行话；
  也刻意避开"孕妇"（普通食品不应针对特定人群宣称）
- **字数预算先给卖点**：属性词加进来之前先给卖点留出余量，避免"属性塞满、一个卖点都没有"
- **去冗余**：名称已含的数字规格不再追加（不会出现 `70g×6瓶 … 70g*6`）；
  卖点里与商品名重复的分句也不重复拼 —— 判重不看子串，按 3 字窗口算重合度，
  所以「印尼溯源干燕盏 … 印尼溯源码燕盏」这种**换个说法复述**也能识别出来；
  整条卖点都被判重复时顺延到下一条，而不是让标题一个卖点都不剩
- **两类生成**：LLM（受规则约束，不合规带反馈重写一次）→ 仍不合规回退模板
- **打分**：字数 / 核心词位置 / 品牌 / 禁词 / 卖点覆盖 / 重复堆砌（满分 95）

同一个 SKU（`DEMO-YW4A50` 印尼溯源干燕盏 4A 50g）在四个平台的真实输出：

| 平台 | 字数 | 标题 |
| --- | --- | --- |
| 淘宝 | 28 | `印尼溯源干燕盏 4A 50g 燕语堂 盏形完整 日常滋养` |
| 天猫 | 23 | `印尼溯源干燕盏 4A 50g 燕语堂 盏形完整` |
| 京东 | 36 | `印尼溯源干燕盏 4A 50g 燕语堂 95干 盏形完整 手工干挑 杂质少` |
| 抖音 | 28 | `印尼溯源干燕盏 4A 50g 盏形完整 手工干挑 杂质少` |

差异不是随机来的，是四条不同的平台约束算出来的：

- **淘宝**（30 汉字）：品牌 + 卖点 + 一个场景词，把搜索词铺得最开
- **天猫**（30 汉字）：品牌必填、型号挪进属性表（天猫审核看属性一致性，不看标题里有没有型号），
  所以标题最短最干净
- **京东**（50 字）：有空间把干度这类参数和两条卖点都放进去，但不要场景词（京东搜索是参数匹配）
- **抖音**（30 汉字）：不带品牌，换成第二条卖点 —— 兴趣电商里卖点比品牌更抓人

这四条都一样受"核心词前置 + 禁词替换 + 不堆砌"的硬约束，只是**在字数预算里怎么分配**不同。
预算有限时先留属性还是先留场景，就是运营的判断。

### ④ 合规检测 `src/ai_agent/compliance_check.py`

**解决**：禁词表又分平台又分品类，人记不住；报错还得告诉人怎么改。

- **三层规则**：平台禁词（绝对化用语）+ 品类禁词（燕窝的功效宣称）+ 正则（手机号/微信/包邮/冒用平台身份）
- **必填字段**：平台必填 + 品类必填合并；资质/发货地这类**商户资料字段只提醒不代填**（不伪造资质）
- **属性一致性**：只对"审核以属性一致为核心"的平台做（京东/天猫），对淘宝/抖音做是误报
- **素材预检**：生成标题**之前**先扫原始商品名/卖点 —— 这才是人工真正踩雷的地方

```bash
$ python -m src.ai_agent.compliance_check --text "顶级印尼燕盏 美容养颜 增强免疫力" \
      --check-platform tmall --category birdnest
[tmall/birdnest] 不通过：顶级印尼燕盏 美容养颜 增强免疫力
  - error banned_word: 《增强免疫力》@ 12 → 建议：营养补充   ← 来自品类规则
  - error banned_word: 《美容养颜》@ 7 → 建议：日常滋养      ← 来自品类规则
  - error banned_word: 《顶级》@ 0 → 建议：高品质            ← 来自平台规则
  - error banned_word: 《养颜》@ 9 → 建议：日常滋养
  - error length: 17 → 字数少于下限 20
```

同一个词换个品类就不报（`--category food` 时"美容养颜"不在该品类禁词表里）—— 这正是把规则拆成两层的目的：
**平台层管"所有商品都不能说"的话，品类层管"这个品类额外不能说"的话。**

### ⑤ 信息抽取 `src/ai_agent/info_extractor.py`

**解决**：品牌方发来的是一段微信文字，不是表格。

- **正则管数字**：净含量/干度/唾液酸/溯源码/条码/保质期，单位统一（`80g`、`×6瓶`、`≥12%`）
- **LLM 管语义**：适用人群、卖点归纳、场景（正则抽不到的才让模型补）
- **完整度按品类算**：燕窝资料看"产地/净含量/保质期/储存/溯源码"，硬件资料才看"材质/容量/尺寸"
  —— 用一张固定字段表卡所有品类，完整度永远是 0
- 输出**完整度**与**缺失字段**，把"漏填"变成"显式待办"

```bash
$ python -m src.ai_agent.info_extractor --input data/raw/产品资料.txt --offline
[INFO] 抽取完成：完整度 100.0%，缺失字段 无
{"产地": "印度尼西亚 加里曼丹", "净含量": "80g", "盏型": "6A 燕盏", "干度": "98 干",
 "唾液酸": "≥12%", "溯源码": "CAIQ-3391-0088", "检验检疫证明号": "JK-2026-0912-ID", ...}
```

### ⑥ 影刀 RPA `src/rpa/shadow_robot_flow.py`

**边界**：Python 不操作浏览器，只把上架任务编译成**任务包 + 步骤契约**。

**步骤数不是写死的，由 `config/platforms.json` 的 `publish_flow` 决定**：

| 平台 | 步骤数 | 顺序（真实后台字段顺序） |
| --- | --- | --- |
| 淘宝（千牛·淘宝卖家中心） | 13 | 选择类目 → 商品图片 → 商品标题 → 商品卖点 → 商品属性 → 价格与库存 → 商品条码 → 物流服务 → 详情描述 → 资质信息 → 提交 |
| 天猫（天猫商家中心·发布宝贝） | 14 | 同上，在"商品标题"后插入 **品牌**（天猫必填、且会审） |
| 京东（京麦） | 11 | 选择类目 → 基础信息（名称+标语） → 商品属性 → **销售属性** → 商品图片 → 商品介绍 → 物流与售后 → 资质 → 提交 |
| 抖店 | 11 | 选择类目 → 品牌 → 商品名称 → 商品主图 → **规格与库存** → 物流 → 商品详情 → 商品资质 → 提交审核 |

（步骤数含 2 个入门动作：打开工作台、选择发布模式。）

- **每个步骤带控件类型**，不是一句"填属性"：`category_picker` / `image_space` / `text` / `select` /
  `sku_matrix` / `logistics` / `richtext` / `upload` / `submit`。影刀按控件类型选不同的录制块。
- **类目是选择器不是输入框**：类目一旦确定，后面能填的属性、能传的图片尺寸、能选的运费模板全部随之变化，
  且**不可改**（要改只能放弃这条重新选）。任务包里带 `category.immutable = true`。
- **SKU 是表格不是单值**：`sku.rows[]` 一个售卖规格一行，逐行给价格 / 库存 / 商家编码。
  价格按行录入，不做乘法。
- **属性是下拉不是文本框**：有枚举的（产地、盏型、干度、储存）给选项列表并标红星必填；
  只有溯源码这类没有枚举的才手输。
- **图片是分栏的坑位，不是"5 个同尺寸方图"**：任务包里是 `images.slots[]`，每栏带
  `ratio / min_px / max_mb / formats / required`。京东的六类栏位、白底图只收 jpg、透明图只收 png 都在配置里，
  不在代码的 if 里。
- 四个后台控件名确实不同：淘宝"商品标题/一口价"、天猫"宝贝标题/宝贝类目/数量"、
  京东"商品名称/京东价/商品条码"、抖音"商品标题/售价/商品编码"。
- **结果是三态**：`submitted` 提交成功 / `draft` 存草稿 / `failed` 被拦。
  抖店缺主图视频时后台不报错、只把商品存进草稿箱，所以仿真也判 `draft` ——
  把草稿算成成功，等于演一套不存在的流程。
- `--dry-run` 走仿真执行，逐步骤打印 + 生成仿真日志，**没装影刀也能演示**。

> 与真实后台逐项对账（哪个视频章节对应哪个阶段、哪些是我原来排错的）见 **[docs/平台实操对照.md](docs/平台实操对照.md)**。
> 可视化配置（登录、等待异步类目面板、图片顺序、失败回写、断点续跑）见 **[docs/rpa_setup.md](docs/rpa_setup.md)**。

## 输入只有基础信息怎么办

真实里两种表都会碰到：品牌方给的资料齐全（品名 / 卖点 / 参数 / 条码），
商家自己维护的进销存表只有六列。系统对这两种输入的处理方式不一样。

| 输入形态 | 典型列 | 能自动做到 | 必须人来 |
| --- | --- | --- | --- |
| 品牌方资料表 | 品名 / 品牌 / 型号 / 类目 / 价格 / 库存 / 卖点 / 参数 / 图片 / 条码 | 全链路 | 复核标题与图片 |
| 商家基础表 | 商品名称 / 品类 / 规格 / 售价 / 库存 / 图片 | 属性反解 + 标题初稿 + 任务包 | 补卖点、补溯源码/保质期/储存 |
| 一段微信文字 | 无结构文本 | 正则抽数字与关键字段 | 人工确认结构化结果 |

### 「商品名称」本身就是一份资料

`src/data_processing/enrich.py` 把名字里**已经写了**的属性抄进结构化字段：

```
"印尼干燕盏 4A 50g"  →  产地=印尼 · 盏型=燕盏 · 等级=4A · 净含量=50g
```

三条规矩：① 表里已有的字段优先，不会被名字覆盖（`产地：印度尼西亚 加里曼丹` 保持原样）；
② 「规格」列填的是 `70g*6瓶` 这种纯度量值时，直接当净含量；
③ 每个反解出来的字段都记进 `specs_derived`，报告里能一眼看出"这个值是机器抄的还是人填的"。

**不做什么**：不生成品牌方没写过的事实。溯源码、保质期、储存条件、条码、产地证明只能人给 ——
猜出来的必填项填进后台就是虚假宣传，比自己填错更麻烦。所以这类字段缺就是缺，列成待办交回运营。

### 实测：同一套代码，换一张表

```bash
python -m src.main --input data/raw/商家自用基础表.xlsx --dry-run --offline
```

| 指标 | 品牌方资料表（36 SKU） | 商家基础表（8 SKU） |
| --- | --- | --- |
| 属性反解 | **21 个**（品牌方表里也有"名称写了、字段没填"的） | **28 个**（8 个 SKU 各 3–4 项） |
| 标题平均分 | 95.0 | 淘宝 85.0 / 天猫 58.8 / 京东 50.0 / 抖音 85.0 |
| 仿真结果 | **99 提交 / 33 草稿 / 12 被拦** | **10 提交 / 8 草稿 / 14 被拦**（14 条全是"标题过短"，8 条草稿是缺主图视频） |
| 字段齐备可提交 | **27/36** | **0/8**（缺的全是人才能给的信息） |

差在哪，报告里写得很直白：

- **没有卖点** → 标题只能拼「品名 + 属性 + 场景词」，每条扣 10 分；
  京东要求 20 字以上，14 字的标题直接被前置校验拦下（**系统不会为了凑字硬塞词**，硬塞就是堆砌）
- **没有品牌** → 天猫把"品牌"设为独立必填阶段，缺品牌时标题分从 85.0 掉到 58.8；
  淘宝/京东同样要求品牌，抖音可不带品牌 —— 这条差异是配置里 `require_brand` 控制的，不是写死的
- **没有溯源码/保质期/储存** → 燕窝类目必填项缺失，后台提交不了
- **系统不替品牌方编溯源码** —— 编出来的必填项过审了也是隐患

产出 `data/processed/enrich_log.md` 直接把待办列出来：

| SKU | 建议 |
| --- | --- |
| `DEMO-0001` | 没有『卖点』列：标题只能拼「品名 + 属性 + 场景词」…补 3 条短语（如 手工干挑;一盏一泡;礼盒装）即可恢复 |
| `DEMO-0005` | 属性缺 产地（后台参数面板会留空或需手填；名称里没写就只能人工补） |

**结论**：基础表能跑到「清洗 → 属性补全 → 标题初稿 → 任务包」这一段，省掉的正是最机械的部分；
卡住的地方是只有品牌方和工厂才知道的信息。这不是系统缺陷，是分工边界 ——
把边界标出来，比假装什么都能自动化有用。

## 规则配置：平台 × 品类 两个正交维度

这是项目里最值得看的部分：**平台决定"后台怎么填"，品类决定"这个品类要多填什么、不能说什么"**。
两者相乘，而不是写成一堆 if-else。

### 平台层 `config/platforms.json`

| 维度 | 淘宝 | 天猫 | 京东 | 抖店 |
| --- | --- | --- | --- | --- |
| 标题字数（汉字） | 16–30，推荐 30 | 16–30，推荐 30 | 18–50，推荐 50 | 12–30，推荐 30 |
| 标题逻辑 | 关键词铺满抢搜索 | 品牌+品名+属性齐，**品牌须有授权** | 属性与标题一致，品牌型号必填（另有一栏商品标语 ≤45 字） | 短句 + 人群场景，**可不带品牌** |
| 发布流程步骤 | 11 个阶段（13 步） | 12 个阶段（14 步，多"品牌"） | 9 个阶段（11 步） | 9 个阶段（11 步） |
| 必填字段 | 类目/价格/库存/主图/属性 | **+品牌、型号、条码、资质** | **+品牌、型号、条码** | **+类目资质** |
| 图片栏位 | 主图 1:1 ×5 ｜ 3:4 竖版 ｜ 白底 ｜ 长图 2:3 ｜ 视频（选填） | 同淘宝，白底更被看 | **方图/长图 3:4/白底/场景/卖点/透明 六类**，白底只收 jpg、透明只收 png | 主图 1:1 ×9 ＋ **白底图、主图视频必传** |

## 可迁移性设计

这个项目是为"滋补食品 + 四个国内平台"写的，但结构上没有绑死在这件事上。四层解耦：

| 解耦点 | 具体做法 | 迁移时改什么 |
| --- | --- | --- |
| 规则 / 逻辑 | 平台、品类、控件名、标题风格全在 JSON | 只改配置，`main.py` 不动 |
| 数据 / 平台 | 上游只产出 `sku_master` 一份数据 | 换平台不动清洗逻辑 |
| AI / 确定性 | 每个 AI 模块都有兜底路径 | 换模型/断网/没 Key 都能跑 |
| 适配 / 执行 | RPA 只认 `{label, value}` 契约 | 换 RPA 工具（影刀/八爪鱼/UiPath）只换执行层 |

### 三种迁移场景

**1）换个品类（最常见）**

```bash
# ① config/categories.json 加一段（照抄 birdnest 改字段）
# ② config/platforms.json 的 category_alias 补该类目的平台类目路径
# ③ 跑一遍看报告，把误报的禁词/属性顺序调一调
python -m src.main --dry-run --offline
```

不需要改任何 Python。演示数据里已经有三个品类共存（燕窝 / 滋补 / 通用食品），可以直接看效果。

**2）加一个平台**

```bash
# ① platforms.json 加一个 key：title / images / required_fields / compliance /
#    category_alias / logistics_defaults / qualification_docs / enforce_attribute_match
# ② 同一个文件里写 publish_flow：工作台名称 + 入口菜单 + stages[]（顺序、控件类型、字数上限）
#    —— 任务包和演示图都从这里生成，不用碰 Python
# ③ src/ai_agent/title_generator.py 的 TITLE_STYLE 加该平台风格（取几个属性/几条卖点/要不要场景/要不要品牌）
# ④ 品类属性有下拉枚举的，补到 categories.json 的 attribute_options
```

第 ② 步就是这次改版的重点：**平台差异从"代码里的 if"变成了"配置里的一段数据"**。
加平台不再需要改 `STEP_SEQUENCE` 这种东西（它已经被删了）。

**3）只想复用其中一块**

每个模块都能单独用，不依赖主流程：

```python
# 只要"标题 + 合规"这两块能力
from src.ai_agent.title_generator import generate_title
from src.ai_agent.compliance_check import check_text

record = {"product_name": "印尼溯源干燕盏 4A 50g", "brand": "燕语堂",
          "category_key": "birdnest",
          "specs": {"产地": "印尼", "盏型": "4A燕盏", "净含量": "50g"},
          "key_selling_points": ["手工干挑，杂质少"]}

t = generate_title(record, "tmall", offline=True)
print(t["title"], t["score"], t["issues"])

check_text("顶级燕盏 美容养颜", "tmall", category="birdnest").to_dict()
```

## 执行层：为什么是影刀，还能换成什么

我只真正用过影刀，所以 demo 用影刀跑。但"最后一公里"是可以换的 ——
因为这一层只消费一个契约：`payload = {后台控件中文名: 值}` + 一串 `steps`。谁读得懂这个契约，谁就能当执行层。

| 执行层 | 怎么接进来 | 适合谁 | 代价 |
| --- | --- | --- | --- |
| **影刀 RPA**（本项目示例） | 可视化流程读任务包，按控件中文名填表 | 运营自己维护流程，不写代码 | 需装客户端；后台改版要重录元素 |
| 其他 RPA（八爪鱼 / UiPath / Power Automate） | 同样按 `{label, value}` 绑定控件 | 公司已有 RPA 采购 | 中文后台元素定位要自己试；许可成本 |
| Playwright / Selenium（纯代码） | 脚本直接读 `rpa_tasks/*.json` 循环填表 | 有工程能力、想进 CI | 登录态/指纹/验证码要自己扛，长期维护成本最高 |
| 平台开放平台 API | 把 payload 映射成发布接口参数 | 有企业资质、量大 | 授权与审核门槛高；本项目拿不到 |
| 平台自带批量导入（Excel/CSV 模板） | 把 `sku_master` 导出成各平台批量模板 | 类目支持、追求稳 | 字段各平台不同、部分类目/平台不支持 |

小总结：

1. **平台自带批量发布，往往比 RPA 更稳。** RPA 的价值集中在三种场合：该平台没有批量模板、类目不支持批量、同一份数据要适配四个平台 —— 这恰好是代销小团队最常遇到的场合。
2. **换执行层不动上半身。** `sku_master`、标题、合规报告、任务包的格式都不变，所以上面这张表是"可替换"，不是"重构"。

## 运行结果

> 数据为**模拟生成**（36 个 SKU：燕窝 28 个 + 滋补食品 8 个，故意夹带脏数据），
> 可复现：`python tools/generate_demo_data.py && python -m src.main --dry-run --offline`。
> 人工基线按 37.5 分钟/SKU/平台估算，是自查体感值，不是系统化计时。

| 指标 | 结果 |
| --- | --- |
| 上架任务量 | 36 SKU × 4 平台 = **144 条** |
| 脚本耗时 | **约 7 秒**（多次运行 7.2–8.4s 波动）；其中约 6.5 秒是仿真执行**故意加的演示延时**，真实计算不到 2 秒 |
| 人工对照 | 约 90.0 小时（估算）→ 提效 **30.0×** |
| 标题字数达标率 | **100%**（144/144） |
| 标题合规率 | **100%**（144/144，禁词在生成前就被替换掉） |
| 标题自评分 | 平均 **95.0**（规则自评的上限就是 95，见下方说明） |
| 素材侧禁词拦截 | **21 处**（顶级/美容养颜/养颜/增强免疫力/孕妇必备/安胎/补血/术后恢复/纯天然/无添加…）在生成标题前就拦下 |
| 字段齐备可提交 | **27/36**（9 个待补：缺原产地 6、缺溯源码 4、缺储存 1 个、缺库存 1 个、缺条码 1 个，有重叠） |
| 字段补全 | 从商品名反解出 **21 个属性**（21 个 SKU 名称里有、字段里没有的产地/等级），已回填进属性面板 |
| 图片合规 | **33/36** 通过，12 条问题定位到具体文件 |
| 数据质量问题 | 36 行 → 错误 1（缺库存）/ 告警 4（未识别列 1 + 类目未匹配 3） |
| 任务包步骤 | 淘宝 13 / 天猫 14 / 京东 11 / 抖店 11 步，共 **1764 个动作块** |
| 仿真结果（三态） | **提交成功 99 / 存草稿 33 / 被拦 12**。12 条被拦全是「类目未匹配」（3 个非标品 × 4 平台）；33 条存草稿全在抖店 —— 缺主图视频，平台只会存草稿 |
| 测试 | `pytest` **51 passed**（2.4s） |

单 SKU 的时间去向（最直观的一张对比）：

```
人工：  读资料 20min → 写标题 15min → 填 4 个后台 100min → 改驳回 20min  ≈ 155min
本系统：跑脚本 1s → 复核标题/图片 5min → 抽检 2 个平台 3min            ≈ 8min
```

`dry-run` 不会真实发布；真实发布的时间瓶颈在影刀执行（受平台响应与频控限制）。
命令行里那 6 秒多的"仿真耗时"不是真实上架时间，是故意留的节奏 —— 任务越多步长越短（预算封顶 6 秒），
不然后台任务到 144 条时演示得干等半分钟。

**为什么是"99 成功 / 33 草稿 / 12 被拦"而不是 144/144**：仿真不假装成功，它按真实后台的前置条件判 ——
类目没匹配上就点不进下一步，标题超字数就输不进输入框，必填素材缺了后台只会存草稿。

- **12 条被拦**：3 个非标品（没进类目别名表）在 4 个平台都没匹配到类目。这种单本来就要人工选一次类目。
- **33 条存草稿**：全在抖店。白底图 + 主图视频是抖店新规的发布前置，演示集里没有主图视频
  （视频要实拍，脚本不造假文件），所以链接一条都发不出去，只能躺草稿箱。
  **把草稿算成"成功"是最容易犯的自我欺骗** —— 报表好看，链接根本没上线。

**关于"平均分 95.0"要说的实话**：这个分是自己写的规则自评（扣分制，上限 95），
144 条全满分只说明"没有违反任何一条规则"—— 字数达标、核心词前置、没禁词、没堆砌、覆盖到卖点。
它**不代表标题写得比同行好**。真实质量只能靠上架后的曝光/点击/转化回流来验证，那是 Roadmap 里的事。

## 局限与边界

| 局限 | 说明 | 后续 |
| --- | --- | --- |
| 规则只是"够用的初版" | 后台控件名来自实际操作、字数/禁词来自公示规范与品类经验；**没有**逐平台比对规则文档，也没调研商家工作台类工具 | 每季度人工复核一次，规则版本化，改版只改 JSON |
| 流程顺序未逐项登录验证 | 四平台的阶段顺序来自公开运营教程（含千牛上架视频分P）、京东开放平台公告与后台截图比对，**没有登录真实账号逐项点一遍**，更没有逐帧核对视频里的每一次点击 | 拿一个测试店把四个后台的发布页走一遍，录屏后与 `publish_flow` 逐阶段对账 |
| 京东那个视频不可用作流程依据 | 用户给的《京东商品上架助手讲解视频》是**第三方铺货工具的宣传片**，全程没有京麦发布页，也没有章节表；京东的流程靠商家帮助中心与官方图片公告还原 | 找一个真正的京麦后台操作录屏，重新核一遍京东的字段顺序 |
| 素材是占位件 | 白底图/长图由 PIL 生成（白底图符合"纯白、无文字无 logo"）；**主图视频不生成**，因为视频必须实拍 | 真实店铺直接用拍摄/剪辑素材，`data/raw/media/` 放进去即可 |
| 不接任何官方发布 API | 走的是浏览器版商家后台发布页，不是开放平台商品接口（企业资质/开发者审核拿不到） | 有资质后只换执行层，上游不动 |
| 不绕过验证码/风控 | 登录保留人工（扫码/滑块），不做任何破解 | 有资质时改用平台开放平台 API |
| 平台改版即失效 | 后台 DOM 变了要改影刀流程 | 元素库集中管理 + 契约不变；回归用例覆盖关键步骤 |
| 类目映射不完整 | "别名表 + 模糊匹配"，新类目要补配置（演示集里 3 个非标品未命中） | 接类目 API，或用品类树做向量匹配 |
| 只覆盖 4 个渠道 | 淘宝/天猫/京东/抖音；其他渠道没实践过，不预置规则 | 按"加一个平台"三步走扩展，补该渠道实测样本 |
| 禁词表不等于平台最新口径 | 品类禁词是经验汇总，平台规则会变 | 规则版本化 + 定期复核 + 抽检样本回归 |
| 标题分是自评，不是效果 | 95 分只说明没违反规则，不代表点击率好 | 数据回流后做 A/B，用真实转化校准 |
| 标题质量依赖素材 | 卖点写得好不好，直接决定标题上限；只有基础表时标题会明显偏短（京东甚至达不到 20 字下限） | 用高转化标题样本做 few-shot 评估；或接商品详情页/图片 OCR 反推卖点 |
| 补全只抄不猜 | 从商品名能反解的只有产地/等级/规格这类；溯源码、保质期、储存条件不生成，缺就缺 | 与品牌方资料回传流程打通，缺项自动发催办 |
| 无多账号与调度 | 单机单账号顺序执行 | 影刀企业版做队列调度 + 频控重试 |
| 资质不代填 | 食品经营许可、检疫证明等只提示，不伪造 | 与资质管理系统对接，做"资质到期"提醒 |

## Roadmap

- **数据回流**：上架后的曝光/点击/转化回写，反哺标题策略（现在标题只能靠规则，缺效果验证）
- **A/B 标题**：同一 SKU 两个标题分平台跑，用真实转化做选择
- **类目映射升级**：品类树 + 向量匹配替代别名表，解决"新类目未命中"
- **资质台账**：食品经营许可、检疫证明的到期提醒（燕窝类目最容易在这里翻车）
- **Web 界面**：给不写代码的运营用（当前形态适合一人多职的小团队）
