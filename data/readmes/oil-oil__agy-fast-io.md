fast-io 是一个 Antigravity 插件，里面只有一份规则（[`plugin/rules/AGENTS.md`](plugin/rules/AGENTS.md)），没有工具、Hook，也没有 MCP。它改的是 Agent 干活的习惯：怎么找代码、一次读多少、命令怎么写、回答写多长。同样的任务，模型回合更少，桌面版要等的云端审查也更少。

> 这是个人做的非官方插件，和 Google 没有关系。

## 效果

我在一个有 2,000 多个 Swift 文件的真实项目上做了对照测试：同一时段、同一个模型，一组不加规则，一组加规则，每个任务跑 3 到 6 次，再按事先定好的标准答案自动评分。

- 找引用、读懂一段机制、跨模块追踪调用链、多文件改名，这 4 类任务都变快了，幅度在四分之一到一半之间，合计快了将近一半。
- 模型回合大约少了一半。
- 答案质量没有下降，加规则前后都是满分。
- 装到桌面版之后，检索命令大多不再触发云端审查。我自己用了几个小时，要送审的工具调用从四成多降到了两成多。

大模型每次的表现波动很大，同一个任务最快和最慢能差一倍，所以这些数字只能当量级看。

## Antigravity 慢在哪

Antigravity 慢，主要不是读文件本身慢。我翻了自己几个星期的会话记录和桌面版日志，时间大多花在下面几处。

<p align="center">
  <img src="./assets/readme/before-after.webp" width="100%" alt="对比插画：没装插件时，Agent 一次只拿一页，在文件柜和书桌之间来回跑很多趟，每趟都要停在“云端审查”的关卡前等待；装上 fast-io 后，一次把要的页拿齐，走“免审通道”，一趟就到。">
</p>

**模型回合太多。** 模型每想一轮要 10 到 20 秒，工具执行本身只占很小一部分，所以多走一轮就多等一轮。可 Agent 习惯读一个文件、想一下、再读下一个；我的记录里，读文件的回合有将近一半只读了一个文件。它还常常只读几十行，不够再回头补，一个任务就这样拖出十几轮。

**没有原生的搜索工具。** 在桌面版 2.0 里，Agent 能用来看代码的只有 `read_file` 和 `run_command`。要搜代码只能跑 `rg`、`find` 这样的命令，而这些命令正好会撞上下一条。

**桌面版的云端审查。** 每个工具调用执行之前，桌面版会先拿内置的白名单检查一遍。`grep`、`cat`、`ls`、`git log` 这类只读命令直接放行；名单外的命令（包括 `rg`、`find`，以及任何带 `&&`、`;`、重定向的命令）和每一次改文件，都要先送云端小模型审查，每次 2 到 3 秒，可疑或超时还会再审一次。审查和执行是排队进行的，审完才能执行。装插件之前，我的会话里大约 45% 的工具调用都要送审。我没找到能关掉这层审查的设置；`agy` 命令行版本没有这层审查。

**最后的回答太长。** 测试里问“这段机制是怎么工作的”这类问题时，Agent 最后一轮写了一两万字，光这一轮就要一两分钟，占了整个任务时间的六七成。

另外两点也值得知道：

- 常被提到的 `read_file` 800 行上限，其实影响不大。我的记录里，被截断的读取只占 2% 左右。
- 模型也有影响。我的记录里，同样的上下文长度下，Gemini 4 Carbon (High) 每轮比 Argon (High) 慢三成左右。

## fast-io 做了什么

<p align="center">
  <img src="./assets/readme/how-it-works.svg" width="100%" alt="Antigravity 桌面版 Agent 的一个循环：模型每轮想 10 到 20 秒；工具调用先过本地白名单，名单里的命令直接执行，名单外的命令和改文件要先送云端审查，每次 2 到 3 秒；结果回到模型再想下一步。编号 1 到 4 是 fast-io 改变的地方。">
</p>

图里的 4 个编号，对应规则里的 4 件事：

1. **先定位，再一轮读完。** 先用一条 `grep -rn` 拿到所有命中的文件和行号，再在同一轮里并行读要看的位置。一次读够 150 到 200 行，300 行以内的文件整份读，不一段一段往回补。
2. **检索只用白名单里的命令。** 用 `grep`、`git ls-files`、`ls` 这些免审命令找代码，不写 `rg`、`find`、`cd … &&`；glob 加引号，git 参数用长写法。
3. **反正要审的命令，合成一次跑。** `python3`、`npm`、构建、测试这类命令每次都要审。互不依赖的几步用 `&&` 串成一次，只审一次，也少等一轮。
4. **回答先给结论。** 不贴大段代码，不复述读到的内容，一般控制在 1,500 字以内。想要详细说明时，直接跟它说“详细讲”。

另外还有几条小规则：小改动用 `edit_file`，同一文件里相邻的几处合成一次改；小任务不写计划文档。完整规则不到 70 行，可以直接看 [`AGENTS.md`](plugin/rules/AGENTS.md)。

## 安装

需要 Antigravity 桌面版或 `agy` 命令行。

```bash
git clone https://github.com/oil-oil/agy-fast-io.git
```

```bash
agy plugin install agy-fast-io/plugin
```

桌面版不用重启，新开的会话就会用上。没有 `agy` 命令行的话，也可以把 `plugin` 目录直接复制过去：

```bash
cp -R agy-fast-io/plugin ~/.gemini/config/plugins/fast-io
```

装好后新开一个会话，让它找一段代码。如果它先跑一条 `grep -rn`，再在同一轮里读好几个文件，就说明规则生效了。桌面版的 Plugins 面板里也能看到 Fast IO；没出现的话，重启一次 Antigravity。

想暂时关掉或重新打开：

```bash
agy plugin disable fast-io
```

```bash
agy plugin enable fast-io
```

## 局限

- **规则不是强制的。** 模型大多数时候会照做，偶尔不会，比如把几条 `git` 查看命令用 `&&` 串起来，反而触发了审查。
- **改文件的审查省不掉。** 桌面版每次 `edit_file`、`write_file` 都要审，改动多的任务提速会少一些。
- **`grep -rn` 不会跳过 `.gitignore` 里的目录。** 规则要求写明 `src`、`Sources` 这类源码目录；如果模型对含大量构建产物的根目录递归搜索，会比 `rg` 慢很多。
- **测试范围有限。** 只在一个 Swift 项目上做过对照测试。加不加插件的对比用的是 Gemini 4 Argon (High)，Carbon (High) 只测过规则改版前后。
- **白名单会变。** 白名单是 Antigravity 内置的，以后版本变了，规则里的命令清单也要跟着改。
- 规则是用中文写的。
