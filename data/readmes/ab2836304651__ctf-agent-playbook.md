## 这是什么

一套**用多个 AI 面板 + 人类指挥协同打 CTF** 的方法论与速查手册。

不是教程，是**赛场现场用的东西**——判读纪律、时间盒、题型打法、已判死清单。

它来自一场真实的线上夺旗赛（2026-09-13，4 小时，1508 支队）。我们解出 13/15 题，得分 650，排名 328（前 21.8%）。**没解出的那两道题，比解出的更值钱**——它们逼出了这份手册里最硬的几条教训。

### ★ 关键背景：我们只准备了两天

这个排名不是靠技术堆出来的，是靠**流程**。如果你的队伍也面临"没时间准备"，
那么这份手册正好是为你写的 —— 它假设你没有深厚的 CTF 功底，只有**几个 AI 工具和两天时间**。

## 如果只读三分钟，读这五条

> 这五条是整份手册里**最反直觉、也最贵**的。

**① 副手零请求，是它能"开挂"的唯一前提。**
主攻每验证一个猜想 = 1 个请求 + 暴露概率 + 等待；副手每验证一个猜想 = 0 个请求 + 读几个文件。
**凡是能在离线侧解决的问题，都在离线侧解决完**，再让主攻用 1 个请求做终局确认。

**② 每个新目标，先确认"它失败时长什么样"。**
我们那场的靶场**所有逻辑错误都返回 HTTP 200 + `msg` 字段**——照搬通用状态码表会把"登录失败"读成"成功"。
**基线不清，所有"有变化"的观察都不可信。**

**③ 结果只有三态：命中 / 明确失败 / 不确定。**
**「不确定」不是实验结论，是仪器故障报警。**
说不出一句"看到 X 算成功、看到 Y 算失败" → 这个测试就不该发。

**④ 容器/靶机窗口是稀缺资源，别拿它跑离线穷举。**
我们在一台 59 分钟窗口的靶机上跑了 **212 万块**的静态哈希窗口穷举——而那个穷举**本来就不需要靶机**。
窗口只该用于"必须实时交互才能验证"的事。

**⑤ 当多条"独立"分析线收敛到同一结论时，先问一句：它们是不是共享了同一个前提。**
我们四条线（主攻 / 副手 / 盲分析者 / 外部模型）都收敛到"存在一个 32 字节的 X"，然后在**同一个空间**里穷举。
**收敛不证明正确，可能只是共同继承了一个错误框架。**
