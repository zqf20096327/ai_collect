GGUF loader nodes for ComfyUI. This is a fork of [city96/ComfyUI-GGUF](https://github.com/city96/ComfyUI-GGUF) with more quant types, more diffusion models and more text encoders. Node IDs, inputs and the category are the same, so existing workflows open unchanged. All 35 ggml storage types, 26 of them quantized, are handled in torch, on the GPU.

| | city96/ComfyUI-GGUF | ComfyUI-GGUF-Next |
| --- | --- | --- |
| Storage types handled in torch | 15, of them 12 quantized | 35 (all ggml storage types), of them 26 quantized |
| IQ1/IQ2/IQ3, TQ (Unsloth "UD" files) | numpy on the CPU, every layer, every step | torch, bit-exact with gguf-py |
| Diffusion architectures | whitelist of 12 | whatever your ComfyUI detects |
| Text encoders | T5, Llama, Qwen2.5-VL, Qwen3, Gemma 3 | + Gemma 2, Qwen2, Mistral 3, Qwen3-VL incl. 32B, ComfyUI-layout GGUFs |
| Quantized `scale_shift_table`, `modulation` | raw blocks copied into the weight | dequantized on load |
| Conv1d, Conv3d, ConvTranspose, RMSNorm | not quantized | quantized |
| Embedding lookup | whole table dequantized per call | only the looked-up rows |
| Model bigger than free RAM | copied into RAM on first load, ends up in swap | stays memory-mapped, read from the file |
| `convert.py` / `lcpp.patch` architectures | 11 | about 30 |

In the comparisons with upstream the output is the same bit for bit: the Anima image, with and without a LoRA, and the Qwen2.5-VL-7B text encoding. CLIPLoader (GGUF) gives the same image as the stock CLIPLoader.

## Install

You need a working ComfyUI with Python 3.9 or newer. Remove or disable the original ComfyUI-GGUF first: both packs register the same node names, and the one loaded last wins. To disable it, rename its folder to `ComfyUI-GGUF.disabled`. GGUF-Next prints a warning at startup if it finds another copy.

```bash
cd ComfyUI/custom_nodes
git clone https://github.com/Zrn59/ComfyUI-GGUF-Next
pip install -r ComfyUI-GGUF-Next/requirements.txt
```

That installs the current `main`. Changes are in [CHANGELOG.md](CHANGELOG.md).

`requirements.txt` lists `gguf>=0.13.0`, `sentencepiece` and `protobuf`. Nothing is pinned. `torch`, `numpy` and `transformers` are not listed. A package that is already installed is not upgraded or downgraded. MXFP4, NVFP4 and Q1_0 files need `pip install -U gguf`.

### Windows portable

Run from the folder that holds `run_nvidia_gpu.bat`:

```bat
git clone https://github.com/Zrn59/ComfyUI-GGUF-Next ComfyUI\custom_nodes\ComfyUI-GGUF-Next
.\python_embeded\python.exe -s -m pip install -r .\ComfyUI\custom_nodes\ComfyUI-GGUF-Next\requirements.txt
```

## Usage

The nodes are in the `bootleg` category, as in upstream:

| Node | Replaces |
| --- | --- |
| Unet Loader (GGUF) | Load Diffusion Model |
| Unet Loader (GGUF/Advanced) | the same, plus `dequant_dtype`, `patch_dtype`, `patch_on_device`, `compile_dequant` |
| CLIPLoader (GGUF), Dual/Triple/QuadrupleCLIPLoader (GGUF) | the stock CLIP loaders, for `.gguf` and `.safetensors` |

- Diffusion models go in `models/unet` or `models/diffusion_models`. Text encoders go in `models/text_encoders` or `models/clip`.
- Qwen2.5-VL and Qwen3-VL need their `mmproj-*.gguf` in the same folder. The loader matches it by file name without the quant suffix. A single `mmproj` in the folder is used only if its projector type fits the encoder.
- `compile_dequant` (or `GGUF_COMPILE_DEQUANT=1`) compiles the dequant kernels with `torch.compile`. It needs `triton`. The first steps are slower while it compiles. fp16/bf16 values are rounded differently from the regular path; the compiled path is closer to fp32 on every tensor. On few-step models this changes small details of the image, as ComfyUI's own TorchCompileModel does ([comparison](docs/en/quants.md#compile_dequant)). It works together with the TorchCompileModel node.
- LoRAs work with the stock LoRA loaders.
- A model bigger than free RAM is not copied into RAM. Its weights stay memory-mapped and are read from the file. `GGUF_RELEASE_MMAP=1` always copies, as upstream does. `GGUF_RELEASE_MMAP=0` never copies.

Model list, quant types and speed: [docs/en/models.md](docs/en/models.md), [docs/en/quants.md](docs/en/quants.md).

## Speed

RTX 3050 Laptop, 4 GB. One 3072×12288 weight to fp16:

| Type | upstream | Next | Next + `compile_dequant` |
| --- | --- | --- | --- |
| Q4_K | 4.5 ms | 4.5 ms | 0.8 ms |
| Q6_K | 6.3 ms | 6.3 ms | 2.8 ms |
| IQ2_XS | 638 ms | 21.7 ms | 0.6 ms |
| IQ3_XXS | 735 ms | 11.6 ms | 1.0 ms |

A full Anima 2B Q4_K_M step at a 64×64 latent takes 639 ms instead of 724 ms. Peak VRAM is not higher.

LTX-2.5 Q4_K_M is a 15.7 GB file, on a machine with 15 GB RAM, in ComfyUI's automatic memory mode, at 640×352 and 97 frames. Both packs put the same 2.3 GB of weights in VRAM and stream the rest. A step takes 547–580 s with upstream, which copies the weights into RAM and so into swap, and 114–129 s with GGUF-Next, which reads them from the file. Two alternating runs each.

## What it does not do

- Qwen3.5, GPT-OSS and Gemma 4 in llama.cpp tensor layout are not converted. They load only from GGUFs with ComfyUI tensor names.
- Large text-encoder token embeddings are dequantized to fp16 on load, as in upstream.
- With a LoRA, a quantized weight is dequantized and patched on every step, as in upstream. This saves VRAM.
- `compile_dequant` is one switch for the whole process.
- A model bigger than RAM is read from disk on every step, so its speed depends on the disk.

More: [docs/en/README.md](docs/en/README.md). Suggestions: [Discussions](https://github.com/Zrn59/ComfyUI-GGUF-Next/discussions).
